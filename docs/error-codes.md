# Error codes

This page lists every error code of the library: the members of the enumeration `Great.Parts.Cel.Diagnostics.CelErrorCode`. Every error that the library reports has exactly one of these codes. A program tests the code, not the text of the message.

How to read the table:

- `Code` is the number of the member, its value in the enumeration. The numbers are explicit and part of the published contract;
- `Name` is the name of the member;
- `Stage` is the stage at which the error occurs. It follows from the number: 1000–1999 `Parse`, 2000–2999 `Check`, 3000–3999 `Evaluate`, 4000–4999 `Build` and 9000–9999 `Any`. The stages `Parse`, `Check`, `Evaluate` and `Build` are the values of `CelErrorStage`; the codes 9000–9999 occur at any stage, and for them `CelError.Stage` is the only indication of where the error happened;
- `When it occurs` is the summary of the member from its XML documentation;
- `Common cause` is what usually gives the error in an application;
- `Fix` is what to change to make the error go away. For the codes that the packages `Great.Parts.Cel.Protobuf`, `Great.Parts.Cel.Policy` and `Great.Parts.Cel.Filtering` report, it is written in the terms of the package.

The first four columns are built from the members of `CelErrorCode` and their XML documentation, and the repository checks that they match them: a member without a row, a row without a member, and a row with another number, name or stage are errors. `Common cause` and `Fix` are written by hand, and a row with either of them empty is an error too.

| 1000 | `SyntaxError` | Parse | The text does not follow the CEL grammar together with the syntax enabled by the environment. The message says what was expected and what was found. | 1003 | `NestingTooDeep` | Parse | The syntactic nesting or the depth of the syntax tree exceeds its limit, given on the page Limits. Chains of `&&` and `\|\|` do not add depth. ## Parts of an error

Besides the code, the stage, the message and the position, an error has the fragment of the expression it refers to and the parts that its code names: `CelError.Span`, `Subject`, `ExpectedType` and `ActualType`. A program takes them from the error and does not parse the message.

- `Span` is the fragment. It starts at `Location` and runs to the end of the node of the syntax tree that gave the error: the identifier for an undeclared reference; for a call without a matching overload, the call from `(` to `)`; for an operator, the sign of the operator and the operand after it, such as `+ 'a'` in `x + 'a'`; for the root of the expression, from its place to its end. An error at a token, such as a syntax error, has the token as its fragment, and at the end of the text a fragment of length 0. The length counts UTF-16 code units, as the offset and the column do. An error of the stage `Build`, which has no place in an expression, has no fragment: `Span` is `default`, and its length is 0.
- `Subject` is the name the error is about, as the message writes it between quotes, without the quotes. A .NET type is its full name.
- `ExpectedType` and `ActualType` are CEL types, `CelType` values. An error of type checking has the static types that the checker compared. An error of evaluation has the type of the value: for a list or a map without a deeper mismatch, the type with its parameters erased to `dyn`, as the function `type` gives it, such as `list(dyn)`; where the message names the type of the first element, key or value that does not fit a declared type, the same type, such as `list(string)`.
- A part that the code does not name is `null`.

`CelError.ToString()` gives `{Code} at {position}: {message}`, such as `UndeclaredReference at 1:7: undeclared reference to 'totl'`; `{Code}: {message}` without a position; the position is `line:column`, with the name of the source document before it when the error has a position in a document. `CelError.ToDisplayString(expression)` gives the message, the line of `expression` where the fragment starts and, under it, spaces up to the first code unit of the fragment, `^` and `~` for each further code unit on that line. Both texts are for people and are not part of the contract.

## Rules of the codes

- A code is added with an explicit number, the next free number of the range of its stage. Adding a code is not a breaking change, so a `switch` over codes needs a default branch.
- Removing a code or changing its meaning is a breaking change and happens only in a major version.
- A number is never used again. There is no code with the value 0: `default(CelErrorCode)` is not a valid code, and no error has it.
- When the same kind of error can occur at two stages, each stage has its own code. The member of the evaluation stage has the name of the member of the checking stage with the prefix `Eval`, for example `NoMatchingOverload` and `EvalNoMatchingOverload`.
- The contract of a code is its number, name, meaning and stage. The text of the message of an error is not part of the contract: it can become more precise in a minor version, and a program does not parse it.
- The columns `Common cause` and `Fix` of [the table of the codes](#error-codes) are the troubleshooting guide of the library: a new code is added with both, and their text can become more precise in a minor version.
