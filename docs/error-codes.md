# Error codes

This page lists every error code of the library: the members of the enumeration `Great.Parts.Cel.Diagnostics.CelErrorCode`. Every error that the library reports has exactly one of these codes. A program tests the code, not the text of the message.

How to read the table:

- `Code` is the number of the member, its value in the enumeration. The numbers are explicit and part of the published contract;
- `Name` is the name of the member;
- `Stage` is the stage at which the error occurs. It follows from the number: 1000–1999 `Parse`, 2000–2999 `Check`, 3000–3999 `Evaluate`, 4000–4999 `Build` and 9000–9999 `Any`. The stages `Parse`, `Check`, `Evaluate` and `Build` are the values of `CelErrorStage`; the codes 9000–9999 occur at any stage, and for them `CelError.Stage` is the only indication of where the error happened;
- `When it occurs` is the summary of the member from its XML documentation.

The table is built from the members of `CelErrorCode` and their XML documentation, and the repository checks that it matches them: a member without a row, a row without a member, and a row with another number, name or stage are errors.

## Messages of time

The messages of the errors that the functions of time and the time zone database give. The text is not part of the contract (see below) and can become more precise; the code and the place are.

| Code | Name | Message | Place |
| :- | :- | :- | :- |
| 3006 | `Overflow` | `timestamp overflow` or `duration overflow` | the operator `+` or `-` |
| 3007 | `ConversionRange` | `{value} is out of the range of timestamp` or `{value} is out of the range of duration`; `{value}` is the number of `timestamp(int)` or the string | the call |
| 3008 | `InvalidArgument` | `invalid argument to 'timestamp': cannot parse {text} as timestamp` and `invalid argument to 'duration': cannot parse {text} as duration`; also for a constant string, at evaluation | the call |
| 3022 | `TimeZoneNotFound` | `time zone '{zone}' is not found in the time zone database of the environment (version {version})`; without a database, `time zone '{zone}' is not found: the environment has no time zone database` | the call |
| 3023 | `InvalidTimeZone` | `invalid time zone '{zone}': expected 'UTC', an IANA time zone identifier or a fixed offset [+-]HH:MM` | the call |
| 4012 | `TimeZoneDatabaseConflict` | `a different time zone database is already added to the environment` | none: a build error |

`{version}` is the `Version` that the application gave to the database; a database without a version leaves it out. Both errors of a zone occur at evaluation, also for a zone that is a constant.

## Rules of the codes

- A code is added with an explicit number, the next free number of the range of its stage. Adding a code is not a breaking change, so a `switch` over codes needs a default branch.
- Removing a code or changing its meaning is a breaking change and happens only in a major version.
- A number is never used again. There is no code with the value 0: `default(CelErrorCode)` is not a valid code, and no error has it.
- When the same kind of error can occur at two stages, each stage has its own code. The member of the evaluation stage has the name of the member of the checking stage with the prefix `Eval`, for example `NoMatchingOverload` and `EvalNoMatchingOverload`.
- The contract of a code is its number, name, meaning and stage. The text of the message of an error is not part of the contract: it can become more precise in a minor version, and a program does not parse it.
