# Test projects

The tests of the library: `tests/Great.Parts.Cel.Tests` and `tests/Great.Parts.Cel.Properties`. The rules on requirement traits, on the `Examples/` directories and on the test framework hold for every test project of the repository, including the suite runner `tests/Great.Parts.Cel.Conformance` and `eng/tests` ([eng-tests.md](eng-tests.md)).

## Projects

| Project | Targets | Modes | Packages | Contents |
| :- | :- | :- | :- | :- |
| `tests/Great.Parts.Cel.Tests` | `net10.0`, `net11.0` | JIT, Native AOT | `xunit.v3.aot` 4.0.2 | unit tests, one directory per namespace of the library; `Examples/` |
| `tests/Great.Parts.Cel.Properties` | `net10.0`, `net11.0` | JIT | `xunit.v3.aot` 4.0.2, `CsCheck` 4.9.1 | properties without an oracle |
| `tests/Great.Parts.Cel.Conformance` | `net10.0`, `net11.0` | JIT, Native AOT | see the description of the suite runner | the cel-spec suite and the regression corpus |
| `eng/tests` | `net10.0` | JIT | see [eng-tests.md](eng-tests.md) | tests of the own checks |

Common settings:

- `dotnet test` runs on the test platform that `global.json` selects; every project uses the same version of `xunit.v3.aot`, under JIT as well.
- Tests run in two ways: the command `eng/test` runs the xUnit.net runner inside every test module — `dotnet <module>.dll` under JIT once, and for the two published projects also the executable under Native AOT — each with `-result-xml`, so that `test-count` compares two reports of the same kind ([eng-test.md](eng-test.md)); a narrow run in the container, `dotnet test` on Microsoft Testing Platform, is a tool of the developer and is not part of the check.
- The library grants `InternalsVisibleTo` to `Great.Parts.Cel.Tests`, `Great.Parts.Cel.Properties` and `Great.Parts.Cel.Conformance` only.
- Test projects set `IsPackable=false` and turn off, each with a reason, `CS1591` — tests have no XML documentation — and `CA1707` — test method names are `<Situation>_<Expectation>`.
- `ImplicitUsings` is off, as in the library: every `using` is written out, and `IDE0005` rejects the unused ones.
- Where the analyzers of the test framework require a token, a test passes `TestContext.Current.CancellationToken`; a test of cancellation or of its absence passes its own `CancellationTokenSource` or `CancellationToken.None`.
- Tests of the code for `net11.0` only, such as `decimal`, are compiled under `#if NET11_0_OR_GREATER`.
- A test class is named `<Subject>Tests` and lives in the directory of its subject, for example `tests/Great.Parts.Cel.Tests/Values/CelValueEqualityTests.cs`. A test method is named `<Situation>_<Expectation>`, for example `NaN_NotEqualToItself`.

## Requirement trait

A test that checks a requirement of the library names it with the xUnit trait `Requirement`:

```text
[Fact]
[Trait("Requirement", "<code>")]
public void <Situation>_<Expectation>()
```

- **Name.** The attribute is the standard `Xunit.TraitAttribute`; the trait name is always `Requirement`. The value is visible in the reports and selects tests with `--filter-trait "Requirement=<code>"`.
- **Argument.** One requirement code per attribute, a string written exactly as in the requirement catalog: `<category>-<number>`, where the category is `F`, `U`, `R`, `P`, `S` or `+R` and the number has no leading zeros. A requirement of the whole system has the prefix `system-`: `system-<category>-<number>`.
- **Several codes.** One attribute per code:

```text
[Trait("Requirement", "<code 1>")]
[Trait("Requirement", "<code 2>")]
```

- **Place.** On a test method, or on a test class when every test of the class checks the same requirement.
- **Only requirement codes, only in the trait.** The trait holds a requirement code and nothing else: no code of an architecture decision record, no other identifier. In a test, a requirement code appears only in this trait, not in names or comments. The rest of the repository — the library code and its XML documentation, documentation, messages, diagnostics, output of checks and data files — has no requirement codes at all.

## Examples/

`tests/<project>/Examples/` holds only examples of behavior: tests that were written from the specification of the library and state the behavior it promises. Developer tests are never placed there.

- An example is the specification of the behavior. When an example fails, the library is wrong; a change of the library does not change an example. An example changes only together with the behavior it states.
- Every example names what it checks: a requirement with the `Requirement` trait, or a row of a published table with the value it asserts — for an error code, the `CelErrorCode` member.
- Examples may use internal entry points of the library through `InternalsVisibleTo`. They do not use helpers of developer tests, so a change of those helpers does not change an example.
- The namespace follows the directory: `Great.Parts.Cel.Tests.Examples` and nested namespaces by subject.
- A long table of example data is one string constant rather than many `InlineData` attributes: the duplicate check counts tests too ([eng-checks-source.md](eng-checks-source.md#duplicates)).
- Examples run with all other tests of the project, under JIT and, in projects published under Native AOT, under Native AOT.

## Property tests and the seed

The verdict of a property is deterministic: the same code gives the same verdict on every machine and in every run, so the contribution of the properties to the mutation score repeats.

- A property with a small domain checks the whole domain, without a generator. `CelErrorCodeProperties` checks every member of `CelErrorCode`.
- A property with a larger domain builds case `i` from the pair of the seed and `i`, with a loop of its own over `Gen<T>.Generate` of CsCheck 4.9.1. The seed and the number of cases are set in the code; the loop reads no environment variable `CsCheck_*` and has no time limit. The loop is written together with the first property that needs it.
- `Gen<T>.Sample` does not give the verdict: a seed passed to `Sample` fixes only its first iteration, and the other iterations are generated from a seed taken from the clock and the thread. A property calls `Sample` only after its loop has found a failing case, to minimize that case. The smallest case goes into the failure message and does not change the verdict.
- A failing case is reproduced from the seed and its number and becomes a unit test with fixed input.
- Properties do no random search of their own; for the core, `eng/difftest` does it, with a seed taken from the date ([eng-difftest.md](eng-difftest.md)).
- Generated expressions of the core come from `Generators/TypedExpressions.cs` of the project: for a target CEL type it builds a well-typed expression over the standard library of this part — literals, the variables of a fixed environment (one of each type `int`, `uint`, `double`, `bool`, `string`, `bytes`, `list(int)`, `list(dyn)`, `map(string, int)`, `map(int, dyn)`, `type` and two `dyn`), calls, `&&`, `||`, `?:`, indexes, selections and `has()` on maps, the standard macros — within depth 8 and 60 nodes, and bindings of the declared types, a `dyn` variable bound to any kind, one variable in ten unbound. Map keys of a literal are pairwise unequal and of the four key types. The number of cases of each property is set so that the properties of the project together take at most 30 s per target in `eng/test`.
- From the part of application data on, the fixed environment of the generator also has a type source `generated` of two types described at run time — `gen.Item` over a carrier class of the project, fields `n` (`int`), `s` (`string`), `w` (`int_wrapper`), `l` (`list(int)`) and `c` (`gen.Item`), with a `has` delegate for `w` and `c`; `gen.Bag` over a dictionary with the fields `n`, `s` and `c` (`gen.Bag`) — and the variables `o` of type `gen.Item`, `g` of type `gen.Bag` and `j` of type `dyn`. The generator builds selections, `has()` and `==` on `o`, `g` and their field `c`, two levels at most, and `type(o) == gen.Item`. Bindings: `o` alternates a bare carrier and a pair `CelValue.FromObject` created with the case; a carrier holds the values its read delegates return, created with it — `l` an `IReadOnlyList<long>` view, `c` absent, `null` or the pair of another item — so a read allocates nothing in application code; `g` a dictionary, sometimes without a key or with a value of another type, which gives `FieldNotSet` and `FieldTypeMismatch`; `j` a `JsonElement` of a document parsed once for the property and kept alive to its end — objects, arrays, numbers, strings, `null`, without repeated names — whose expressions are selections, `has()`, indexes, `size` and `in`. Values compare as in "Properties of evaluation", object values by the same instance and description.

- From the part of time on, the fixed environment of the generator also has the variables `ts` of type `timestamp` and `du` of type `duration`, the database of the whole test archive ([Time zone data](#time-zone-data)) through `UseTimeZones`, and `timestamp` and `duration` among the target types. The generator builds `timestamp(s)` and `duration(s)` with `s` a string of the time grammar of `eng/difftest` ([eng-difftest.md](eng-difftest.md#profile)) — valid and mutated, so errors occur — and `timestamp(n)` with `n` an `int` near the limits of the range; `+` and `-` of time, the relations, `==`, `int()` and `string()` of both types, the ten receivers of a timestamp without a zone and with a zone from the pool `'UTC'`, `'+05:45'`, `'-03:30'`, `'Asia/Kathmandu'`, `'America/New_York'`, `'Mars/Base'`, `''`, `'+1:5'`, and the four receivers of a duration. Bindings: `ts` and `du` take the limits of their ranges and values next to them — seconds −62 135 596 800, 253 402 300 799, 0 and ±1, nanoseconds 0, 1 and 999 999 999, durations 0, ±1, `long.MinValue` and `long.MaxValue`; a `dyn` variable may hold a time value. Values compare as in "Properties of evaluation", time by kind and payload.

## Properties of the parser and the checker

`tests/Great.Parts.Cel.Properties/Syntax/` and `Checking/` hold two classes each. They call the internal `CelEnvironment.Parse` and `CelEnvironment.Check` ([facade.md](facade.md#internal-entry-points)), so the compilation boundary is part of what they check. The parse of every expression of the cel-spec suite is a test of the conformance runner ([conformance.md](conformance.md#parse-test-of-the-cel-spec-suite)).

- `ParserProperties`, each with the loop of the previous section and the number of cases set in the code:
  - `NeverThrows`: generated strings up to 64 KB — random characters, random tokens, grammatical texts, among them nesting deeper than 250 and more than 100 syntax errors. `Parse` returns; no exception escapes; no error is `InternalError`; every error lies within the text. A generator knows the limit its text goes over, and the result then has `ExpressionTooLong`, `NestingTooDeep` or `TooManyErrors` with its position.
  - `RoundTrip`: grammatical texts within the limits, from the whole grammar with the optional syntax and the standard macros, parse; printing and parsing again gives a tree without a difference by `SyntaxTreeComparer` ([syntax.md](syntax.md#printing-and-tree-equality)).
  - The failure message names the property, the seed and the number of the case, then the reason and the smallest case.
- `WorstInputTests`, one test per input, each at most 65 536 UTF-8 bytes: the deepest nesting allowed for each kind of nesting; chains of each binary level, `&&` and `||` included, filling 64 KB; a text with more than 100 syntax errors; 64 KB of garbage from a fixed seed. A test parses its input once to warm up and once under `Stopwatch`, asserts that no error is `InternalError` and writes `<input>: <seconds> s` to the test output.

- `CheckerProperties` (type checking), in an environment of `CelStandardLibrary.V1` with the variables of the generator:
  - `NeverThrows`: the grammatical texts of `ParserProperties` that parse, and texts of the generator with one node replaced by a node of another type. `Check` returns; no exception escapes; no error is `InternalError`; every error lies within the text.
  - `WellTyped`: the expressions of the generator check without errors, and their `ResultType` is assignable to the target type ([types.md](types.md)).
- `CheckerWorstInputTests` (type checking), one test per input of at most 65 536 UTF-8 bytes, timed like `WorstInputTests` for parse and check together: the inputs of `WorstInputTests` that parse; list literals filling 64 KB whose elements are `x + x` with `x` of type `dyn` (every candidate of `_+_` per call), `[]` (a fresh type variable per element, all joined), alternating `1`, `1u`, `1.0`, `'a'` (joined to `dyn`), and `1 + 'a'` (one `NoMatchingOverload` per element); nested list literals 250 deep; a chain of 250 `_+_` over `[]`; comprehensions nested as deep as the parser allows; a selection chain of 250 names `a.a.….a` in a container of 250 segments `a.a.….a`, so that every prefix of the chain meets every candidate of the container.

**Where the time limit blocks.** A time over 1 s fails a worst-input test, with the message `<input>: 1.42 s > 1 s`, only on the reference machine: a standard GitHub-hosted Linux x64 runner, recognized by the variables that GitHub Actions sets on every runner — `GITHUB_ACTIONS` is `true`, `RUNNER_OS` is `Linux`, `RUNNER_ARCH` is `X64` and `RUNNER_ENVIRONMENT` is `github-hosted`. In `ci.yml` these are the JIT cells on `ubuntu-latest`: the project runs only under JIT, and the Native AOT job runs only the published projects. Everywhere else — `eng/test` and `eng/mutate` in their containers, the cells on `macos-latest`, a machine of a developer — the time is only written, so there the verdict does not depend on time and repeats. `ci.yml` sets no variable of its own for this.

## Properties of evaluation

The failure message of each property names the property, the seed and the number of the case, then the reason and the smallest case, as for the parser.

- **`Evaluation/CheckedEqualsUncheckedTests.SameResult`**. For each case of the generator: `Compile<CelValue>` and `Evaluate`, and the internal `Parse` and `EvaluateWithoutTypeCheck` of the same text and bindings. Both give a value, or both an error; two values are equal by a structural comparison of the test — the same kind, lists element by element, maps as sets of entries, NaN equal to NaN, type values by `Name`. Error codes are written into the failure message, not compared.
- **`Facade/ConcurrencyTests.ParallelEqualsSequential`**. One environment of the generator, with two application functions — a typed delegate and a `CelFunctionImplementation` — and 64 texts with 16 bindings each. The reference results are computed first on one thread. Then 64 threads, created with `new Thread` and started together by a `Barrier`, each run every item of four scenarios in an order of their own: `program.Evaluate` of one program per text on its bindings; `env.Compile<CelValue>` of the texts and the evaluation of each result on its first bindings; `env.Evaluate<CelValue>` of text and bindings; `GetOrCompile<CelValue>` and `Evaluate<CelValue>` of one `CelCompilationCache` whose capacities hold 16 entries, so that eviction runs under contention. Half of the evaluations have a cost limit. The objects of the application, the `JsonElement` and the carriers of types described at run time of the generator are bound in every case, so the threads read the same instances, descriptions and documents at once. Each result must equal its reference: values by the comparison of `CheckedEqualsUncheckedTests`, compile results by `ResultType` and by the code, stage, message and location of each error, evaluation errors by code, message and location. An exception of a thread fails the property with the thread and the item.
- **`Evaluation/CostTests.AllocationWithinCost`**. For a program and bindings, with the limit `ulong.MaxValue` the property measures the bytes that `GC.GetAllocatedBytesForCurrentThread()` counts beyond the frame and the units charged: `Plan` gives the two steps of `Plan.Evaluate` as internal members — `Frame CreateFrame(bindings, costLimit, cancellationToken)` and `CelValue Run(Frame frame)` — and `Frame.ChargedUnits` is the limit minus the remaining units. Bytes are counted from after `CreateFrame` to the end of `Run`, as the smallest of three evaluations after the first, so that one-time initialization is not counted and neither are the few KB that the JIT runtime allocates on the test thread when it moves methods between tiers (2 of 20 runs; none with `DOTNET_TieredCompilation=0` and none under Native AOT): the program allocates its bytes in every evaluation, the runtime noise only in some. Bytes ≤ units × B with B = 64, a constant of the test; where the evaluation stops at the limit, the bytes of the stop itself are added: S = 2 048, a constant of the test (`StopBytes`), above the 0.8–1.4 KB that the `CostLimitException` with its stack trace and the error value take. Where the evaluation of a case of the generator ends in an error value that is not the stop by the limit, the bytes of the error are added: E = 256, a constant of the test (`ErrorBytes`), above the error object and the message with the names of the program, which the generator keeps short (the largest excess over units × B in 6 000 cases was 128 bytes, `Unbound`; `FieldNotSet` takes 160 bytes for 2 units). E is not added when the stop by the limit adds S. Inputs: the cases of the generator, and one row test per row of the cost table of this part whose memory grows with the data — list and map literals, `add_list`, `add_string`, `add_bytes`, the conversions to and from text, `map` and `filter`, `contains` with a pattern over 256 code units — each on data of sizes 0, 1, 10, 100 and 1 000, bound as variables of type `dyn` where a literal would be long, so that the check of a binding ([values](values.md), "Fits a type") charges nothing and does not lower the bytes per unit of the row. The literals have literal elements, keys and values — `[1, 1, …]` and `{0: 1, 1: 1, …}` — which cost 0, so the row charges only the literal itself, the strictest case. Two more rows measure error values: `1 / 0`, an operation of 1 unit that fails, the same on every size, and `int(x)` with `x` a text of the size that does not parse, `a` repeated, whose message holds the text. These two rows keep B per unit without E. The part of time adds the rows `string(timestamp)` and `string(duration)` over the values with the longest texts, and two rows of errors of 1 and 2 units, `timestamp(i)` with an `int` outside the range and `ts.getHours(z)` with `z` bound to `+1:5`, which keep B per unit without E ([evaluation.md](evaluation.md#time)). Two rows measure the check for repeated names of a JSON object, whose set grows with the names charged ([values](values.md), "`JsonElement`"): `size(x)` (`size, JSON object`) and `'k0' in x` (`in, JSON object`) with `x` a `JsonElement` object of n properties named `k0`, `k1`, … with the value 1, bound as a variable of type `dyn`, n of 0, 1, 10, 100 and 1 000; an object of 0 or 1 properties builds no set. Calibration: the largest number is 52.5 bytes per unit, at 10 properties, so with B = 64 the margin is about 18 %; these rows too keep B per unit without E. Three rows measure the copies of arguments of an application function ([evaluation](evaluation.md), "Application functions"): `f(x)` with `x` of type `dyn` and a typed delegate that returns the count or the length without reading the elements — `Func<IReadOnlyList<int>, long>` for `list(int)`, `Func<IReadOnlyDictionary<string, int>, long>` for `map(string, int)`, `Func<byte[], long>` for `bytes`. The keys of the map are the strings `"0"`, `"1"`, …, which the copy charges ⌈L/10⌉ each. Since the check of the argument charges n without memory, `Values/ConversionRulesTests` also measures the copy alone, its bytes against its own units, on 0, 1, 2, 8, 9, 100 and 1 000 elements or pairs and L of 0, 1, 10 and 1 000. A row test writes `<row>: <max bytes per unit> bytes/unit` to the test output; these numbers are the calibration of the rows of this part (stage 0, item 6), and the task that measures puts them into its report. Another row stops the loop by a limit: `map` and `filter` over a `dyn` list of 1 000 elements with the limits 2, 3, 10 and 100, bytes ≤ B per unit charged at the stop plus S. A row that does not fit B is not fixed by raising B: its formula or its allocation changes.
- **`Library/SubstringSearchLinearityTests.StepsBounded`** (`contains`). It calls `SubstringSearch.IndexOf(text, pattern, ref steps)` ([library.md](library.md#substring-search)) and asserts steps ≤ 4 · (n + m), n and m the lengths in UTF-16 code units, and the index equal to that of a naive search written in the test. Inputs: text `(ab)^N` with pattern `(ab)^k` and another last unit; `a^n` with `a^(m−1)b`; a pattern equal to a prefix of the text; a pattern longer than 256 code units; an empty pattern; a pattern longer than the text; surrogate pairs; random strings over alphabets of 2 and 3 code units. n reaches 1 000 000. No time is measured.

## Environment from JSON

**`Configuration/EnvironmentJsonTests.JsonEqualsBuilder`** in `Great.Parts.Cel.Properties`: an environment from a description in JSON equals the environment that the equal builder calls give ([configuration.md](configuration.md)). Case `i` comes from the seed and `i` by the loop of "Property tests and the seed".

- **Generated.** A model of a description: `name`, sometimes missing; `container`, empty or a qualified name of 1–3 segments; 0–6 variables with simple and qualified names; 0–4 functions of 1–3 global or receiver overloads, with type parameters `~A`, `~B`; 0–3 object types of `greatPartsCel` with 0–4 fields each. Types are type records of the whole grammar the reader maps — simple types, `dyn`, `null_type`, wrappers, `type`, `list` and `map` up to depth 2, the object types of the model. Names are drawn from small pools, so repeats occur and give build errors: a variable declared twice with two types, an object type twice, one overload id twice, overlapping overloads, a name that is not an identifier, an object type that no source declares. Both builders first get the same calls in code, drawn from: `UseContainer` with another value, a variable, a provider with a type of the model's name; so conflicts between code and JSON occur on both sides alike.
- **Printed twice.** As JSON — keys in random order, random white space, `type` or `type_name` with `params`, escapes in strings — passed to `Apply`; and as the equal calls: `UseContainer`, `AddVariable(name, type)`, `AddFunction(CelFunctionDecl)`, `AddTypes(CelTypeProvider.Create(label, …))` with `ForDictionary` types. For every overload both builders register the same `CelFunctionImplementation`, which returns a fixed value that fits its result type with type parameters as `dyn` — `null` for an object type and a wrapper. Field names of one type are distinct and names of object types qualified, so `Apply` never fails.
- **Compared.** `Build`: both succeed, or both fail with the same codes in the same order (messages differ only by the names of sources). Then, in both environments, a set of texts: each variable; `type()` of it; each field of an object variable with `.` and `has()`, one level deep; each overload called with variables or literals of its parameter types; each name through the container, by its shortest form and with a leading `.`; and a name that is not declared. Compile results by `ResultType` and by the code, stage, message and location of each error; values of one set of bindings — a value of each declared type, dictionaries for the object types, one variable in five unbound — by the comparison of "Properties of evaluation"; evaluation errors by code, message and location. 100 % of the cases agree; the failure message names the property, the seed, the number of the case, the first difference and the JSON text.

## Allocation of an evaluation

**`Allocation/EvaluationAllocationTests.WithinBudget(scenario)`** in `Great.Parts.Cel.Tests`, a theory over the name of the scenario with the trait of the performance requirement it serves: the evaluation of a compiled program on objects of .NET allocates at most the budget of its scenario, 0 bytes when it creates no new value. It runs in `eng/test` under JIT and Native AOT, like every test of the project. The test uses only the library: no other library, no benchmark, no result of a comparison.

- **Data.** Classes of the test `Order` — `Id`, `Status`, `Currency` (`string`), `Total` (`double`), `Discount` (`double?`), `Created` (`DateTimeOffset`), `Lines` — and `OrderLine` — `Sku` (`string`), `Qty` (`long`), `Price` (`double`). Types `shop.Order` and `shop.OrderLine` by `CelObjectTypeBuilder<TCarrier>`, in a provider added with `AddTypes`; the field `lines` has the type `list(shop.OrderLine)`, `discount` the type `double` with the `has` delegate `Discount is not null`, `created` the type `timestamp`, read as `CelValue.FromTimestamp(CelTimestamp.FromDateTimeOffset(order.Created))`, which allocates nothing. Orders of 10 and 100 lines: line i has the SKU `SKU-` and i in four digits, the quantity `i · 3 mod 20 + 1`, the price `10 + 1.5 · i`; the order has the id `ORD-0001`, the status `approved`, the total 1 500, the currency `RUB`, the discount 100 and `Created` 2026-11-01T12:00:00Z. Variants: without the discount, and with only the last line's SKU starting with `SKU-` (the others `ITEM-`).
- **Binding.** `order` is a variable of type `shop.Order`, bound to `CelValue.FromObject(orderType, order)` created once; the read delegate of `lines` returns a `CelList` of pairs `FromObject(lineType, line)` built once with the order, so reading `order.lines` and `l.qty` on a pair allocates nothing. A `CelList.CreateView` with a converter that calls `FromObject` would create a pair per element at each evaluation, and a bare carrier a pair at the first read: those are budgets of the binding, not of the library, and the test does not use them.
- **Scenarios.** `E1` `order.total > 1000.0 && order.status == 'approved'`; `E2` `order.lines.all(l, l.qty > 0 && l.price >= 0.0)` on 10 and 100 lines; `E3` `order.lines.exists(l, l.sku.startsWith('SKU-'))` on 10 and 100 lines, also with the last-line variant; `E4` `order.lines.filter(l, l.qty > 10).map(l, double(l.qty) * l.price)` on 10 and 100 lines; `E6` `has(order.discount) ? order.total - order.discount : order.total`, also without the discount; `E8` `size(order.lines) <= 100 && order.currency in ['RUB', 'USD', 'EUR']`; `E9` `'Order ' + order.id + ': ' + order.status`. `E7` `order.created + duration('72h') > now` on 10 and 100 lines, with `now` a variable of type `timestamp` bound as a `CelTimestamp` one hour after `Created` — the result is `true`; `E5`, with `matches`, joins with the part that brings `matches`, and its name stays free.
- **Budgets.** A constant next to each scenario with its reason: 0 for E1, E2, E3, E6 and E7 — E7 keeps the moment in the payload of the value and folds `duration('72h')` at planning, so nothing is created; E4 the two lists that `filter` and `map` create, with their growing arrays, as a function of the count of lines that pass; E8 the list of the literal, 144 bytes — the array of its 3 values, 120, and the list object, 24; the plan builds a literal of constants at each evaluation, and a node that builds it once is an optimization of the speed stand, not a requirement of this test; E9 the three strings of the concatenations, 184 bytes. Measured on 10 lines with 3 passing: E4 is 504 bytes, and 100 lines with 50 passing 9 464. A number comes from the measurement below, the greatest seen; a budget of 0 must hold in every configuration.
- **Measurement.** `Compile<bool>` (`CelValue` for E4, `double` for E6, `string` for E9) once, then the program is evaluated once, unmeasured, so that one-time initialization is not counted. Then three times: `Plan.CreateFrame(bindings, null, CancellationToken.None)`, and `GC.GetAllocatedBytesForCurrentThread()` around `Plan.Run(frame)` alone ([evaluation.md](evaluation.md), "Frame"). The verdict takes the smallest of the three, so the few KB that the JIT runtime allocates on the test thread when it moves methods between tiers are not counted; the program allocates its bytes in every evaluation. The test also asserts the result value of each run. A second assertion measures the public call `program.Evaluate(bindings)` the same way: at most the bytes of `Run` plus `FacadeBytes`, a constant of the test, 512 (the greatest addition of the public call measured is 440) — the frame with its slots and argument stack, and the result object — so the facade adds no allocation that grows with the data. The test writes `<scenario>: <run1> <run2> <run3> bytes, facade <n> bytes` to the test output.
- **Determinism of the count.** The task that writes the test runs it, in the container, under JIT three ways: the default; `DOTNET_TieredCompilation=0`, optimized code only; and `DOTNET_TC_CallCounting=0` with `DOTNET_TC_OnStackReplacement=0`, unoptimized code throughout. It sets each budget by the greatest number seen and writes the numbers of each way into its report. `eng/test` then adds the published run under Native AOT. When the three numbers of one run differ, or a budget of 0 holds only with optimized code — the optimizer placed an object on the stack — the code of the library changes, not the budget: no path relies on the optimizer.

## Snapshots of the extension sets

The declarations of each version of each set are pinned by a snapshot, as those of the standard library are: a later change of a published version is a failing test, and a new function comes as a new version. `Library/LibrarySnapshotTests` in `Great.Parts.Cel.Tests` gets one `[Fact]` per set, `StringsV5`, `MathV3`, `ListsV4`, `SetsV0`, `EncodersV1`, `BindingsV1`, `TwoVarComprehensionsV0` and `NetworkV1`; each builds the text of its version with the writer that `StandardLibraryV1` uses and compares it with a file under `tests/Great.Parts.Cel.Tests/Library/Snapshots/`, named `<set>-v<version>.txt` with the name of the set as the catalog has it (`two-var-comprehensions-v0.txt`). The message of a failure names every line that differs.

The text of a set begins with a header and lists, in the order of the table of the set:

```text
set strings 5
depends <name>                          one line for each dependency; none in this release
type net.IP                             one line for each abstract type
macro math.greatest receiver *          name, global or receiver, the argument count or * for any
overload <function> <id> <global|receiver> <parameter types> -> <result type> cost <c0> <c1> <c2> <c3> <c4>
```

An `overload` line is that of the snapshot of the standard library: the function as the tree names it (`math.@max`, `strings.quote`, `cel.@block`), the identifier, the call style, the types in their text form with type parameters as written, the flag `dyn` for an overload that is a candidate only with a `dyn` argument, and the cost of five probes — all arguments of the kinds `string` and `bytes` of the length s, lists and maps of s entries, an `int` equal to s, a `double` of 1, and a `net.IP` or `net.CIDR` of fixed value — for s of 0, 1, 10, 11 and 100. The number is `FixedCost` and `ArgumentCost` alone, the part known before the call: what an implementation charges while it runs is in the rows of [library](library.md#cost-of-the-extension-sets) and not in the snapshot, so the probe does not run it. The flags `ShallowArguments` and the validator are not recorded: they are behavior, not declaration.

The files are written by running the writer on the declarations, once, after the mechanism of the snapshot of version 1 exists; a published version is changed only by a change that does not add a new version.

## Substring search of the extension sets

**`Library/StringSearchLinearityTests`** in `Great.Parts.Cel.Properties`, with the tests `IndexOfStepsBounded`, `LastIndexOfStepsBounded`, `ReplaceStepsBounded` and `SplitStepsBounded`, beside `SubstringSearchLinearityTests`. Each calls the internal implementation of the function with the counter, `StringFunctions.IndexOf(text, pattern, offset, ref steps)` and its kind for the other three ([extension-strings](extension-strings.md#search)), and asserts steps ≤ 4 · (n + m), n and m the lengths in UTF-16 units, and the result equal to that of a naive reference written in the test over code points with the semantics of the page for n up to 4 096 and for random inputs; for the chosen worst inputs the result is known from the construction of the input and is written beside it: the offset and the empty cases, the limit `n` of `replace` and `split`, the empty pattern. Inputs, each for every one of the four where it applies:

- text `(ab)^N` with the pattern `(ab)^k` and another last unit, and with `(ab)^(k−1)aa`;
- text `a^n` with the pattern `a^(m−1)b` and, for `lastIndexOf`, with `b a^(m−1)`, whose first unit differs where the search starts from the end;
- `replace` with an old string that matches many times — `ab` in `(ab)^N`, `aa` in `a^n` — and one that matches never, and a long new string; `split` with the separators `a`, `a^k`, `a^(k−1)b` over `a^n`;
- an offset at the start, in the middle, at the end and past the end, and the limit `n` of 0, 1, 2 and more than the matches;
- the pattern equal to a prefix of the text, longer than 256 units, longer than the text, empty;
- surrogate pairs in the text and the pattern, and a lone surrogate in the text;
- random strings and patterns over alphabets of 2 and 3 units.

n reaches 1 000 000 and m 100 000. No time is measured; the bound is on the steps, which count each comparison of two units, the preparation of the pattern included.

## Cost and memory of the extension sets

The rows of `Evaluation/CostTests.AllocationWithinCost` of [Properties of evaluation](#properties-of-evaluation) — the property that measures an allocation against the units charged — for the sets are in `Evaluation/ExtensionCostTests`, which takes the measuring helper `Evaluation/CostRows` shared with `Evaluation/ProtobufCostTests` (separate classes because of CA1506); each on the sizes 0, 1, 10, 100 and 1 000 where it grows with the data, bound as variables of type `dyn` where a literal would be long, and each run twice: through `Compile` and through `Planner.PlanWithoutTypeCheck` with `Plan.Evaluate`, so that the functions of the sets are measured on both paths. - **Errors.** Rows that make the error: a format string with an unknown letter and with a precision of 101, `ip(x)` and `cidr(x)` with `x` a text of the size that is not an address, `base64.decode(x)` with illegal text of the size, `charAt` past the end, `lists.range(-1)`, a duplicate key in `transformMapEntry`. ## Same tests under JIT and Native AOT

`Great.Parts.Cel.Tests` and `Great.Parts.Cel.Conformance` are published under Native AOT and run as executables: in `eng/test` and in CI, on linux-x64, for both targets ([eng-test.md](eng-test.md)). `eng/checks test-count` compares the tests of each published run with the JIT run of the same commit, operating system and target ([eng-checks-artifacts.md](eng-checks-artifacts.md)). The other test projects run only under JIT.

Rules that keep the two sets equal:

- No generic test methods: the test framework does not run them under Native AOT.
- Test data are known when the project is built: inline data and static members, not data found by reflection at run time.
- A test does not skip itself, change its name or its data depending on the mode. `#if` around tests depends only on the target framework. The culture tests choose their culture by the globalization mode and keep their names, data and expectations ([Culture of the process](#culture-of-the-process)).
- The display name of a theory case does not depend on the culture of the process: the JIT run uses ICU, the published run the invariant culture.

Project settings:

- `PublishAot=true` and `RuntimeIdentifiers` with `linux-x64` are in the project files of the two projects. Restore is then the same for JIT and Native AOT: the publish runs with `--no-restore` after a restore without a runtime identifier and changes no lock file, neither of the project nor of the projects it references.
- `UseDefaultPublishRuntimeIdentifier=false` is in the same project files, with its reason: with `PublishAot=true` the SDK takes the runtime identifier of the host as the default publish identifier and appends it to `RuntimeIdentifiers`. On a Linux x64 host that is `linux-x64`, already in the list; on a macOS runner it is `osx-arm64`, the restore then differs from the lock file and a locked restore fails with `NU1004`. The list stays `linux-x64` on every host, and the publish names `linux-x64` with `-r`.
- `DynamicCodeSupport=true` is in the same project files for every build except the publish. With `PublishAot=true` the targets of the Native AOT compiler set `DynamicCodeSupport=false` for every build, and the SDK writes it into the runtime configuration: the JIT run would then run without dynamic code, as the published one, and the conformance runner would name its cell `native-aot` ([conformance.md](conformance.md#skip-lists-and-findings)). The publish keeps `false`.
- `PublishDocumentationFile=false` is in the same project files, with its reason: the Native AOT publish of the SDK looks for the XML documentation file in the runtime output, where the build does not put it, and fails with `MSB3030`. A test executable needs no documentation file; `GenerateDocumentationFile` stays `true`.
- `InvariantGlobalization=true` is given only on the `dotnet publish` command line. The JIT run keeps ICU, the published run uses the invariant mode, and the same expectations hold in both.

Under Native AOT the stack trace of a failed test is cut down: the console and the `<stack-trace>` element of the report show the name of the test and the message, and for a thrown exception the method and an offset, but no file and line. The file and line are in the report of the run: the attributes `source-file` and `source-line` of its `<test>` element, which the test framework records at build time — the file and the line of the `[Fact]` or `[Theory]` attribute, with the absolute path as the build saw it. If a report of a published run has no source for a test, the file and line are found by the test name in the PDB of the JIT build of the same commit, as `test-count` does.
