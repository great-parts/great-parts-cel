# The CEL Policy package and positions in a document

`Great.Parts.Cel.Policy` reads a CEL Policy document in YAML and compiles it in a CEL environment into one program, as cel-go v0.33.4 does (`policy/`). The package uses only the public API of the core; the core gains the points it needs: `CelSourceSegment` with `CelCompileOptions.SourceSegments`, `CelError.Create`, the public constructor of `CelException`, `CelEnvironmentBuilder.AddAbbreviation`, and the typing of the slots of `cel.@block`. Members and their documentation are in the XML documentation of the public API. The YAML reader is on its own page, [yaml-reader](yaml-reader.md).

## Core points

**Segments.** `CelCompileOptions.SourceSegments` is an `ImmutableArray<CelSourceSegment>`; its `init` checks the rules (first at 0, strictly growing, one source name, not together with `SourceLocation`). Every place where the core maps a position of an expression to a position of the document uses one internal readonly struct, `DocumentMap`, built once per compilation from either the segments or the start (`SourceLocation` is a map of one segment): the segment offsets and the lines of their starts sit in arrays for a binary search, and the line table of the expression is read only to find the line of each segment start. `Compile`, `Validate`, `Parse`, `CompileParsed`, `ValidateParsed` and the errors of evaluation in `CelProgram` map through it; the program keeps the map instead of the start. `CelParsedExpr.SourceName` is the name of the document of the segments. The key of the compilation cache holds the segments, compared element by element (an `ImmutableArray` is compared by reference); the hash combines the count and the first and last segment.

A segment on a line break belongs to the line the break ends: the place of the break character is the segment's own place, but its line in the expression is the earlier one. An application that maps a block of a document gives each segment the first character of a line, after the break, as the example of the XML documentation of `SourceSegments` does.

**Errors.** `CelError.Create` builds the error with the location, the length, the parts and no exception; it checks the code and the stage with `Enum.IsDefined` of the generic overload, which needs no reflection and is safe for Native AOT. `CelException(IEnumerable<CelError>)` copies the errors to an `ImmutableArray`, rejects an empty list and a `null` element, and calls the private constructor with the first exception found, as `FromErrors` does.

**Abbreviations.** The builder keeps the names given to `AddAbbreviation`; `AddAbbreviation` rejects nothing itself. `Build()` checks them (`Declarations/AbbreviationChecks.cs`) as `Abbrevs` and `aliasAs` of cel-go do, in the order of `string.CompareOrdinal`, so that the order of the calls changes neither the errors nor which of two abbreviations of one short name is kept: the name is trimmed of white space; it is a qualified identifier with at least two parts and no leading dot (stricter than cel-go, which also takes `a..b`, a part that begins with a digit and a reserved word); a repeated short name is an error even with the same qualified name; a container equal to the short name, or beginning with it and a dot, is an error (a container `x.T` with `a.b.T` is valid). The errors are `InvalidAbbreviation` with the name in `Subject`. The valid ones go to the name resolution of the checker: `DeclarationIndex.TryExpandAbbreviation` and `Checker.CandidatesOf` look for an abbreviation of the first part of a name without a leading dot, and the only candidate is then the qualified name with the rest appended, as `findAlias` of cel-go. The same function serves identifiers, selections, function names and message names. The set of abbreviations is part of `DeclarationSet`, so `ToBuilder()` keeps it.

**Slots of `cel.@block`.** `Checker.VisitGlobalCall` treats a call `cel.@block` whose first argument is a list literal without optional elements as a scope, when the environment does not declare `@index0` itself (the internal `block` set of the cel-spec runner declares `@index0`–`@index29` as `dyn`, and its cases keep their 1.0 types). The elements of the first list are checked in order; after the check of element N the checker declares the local `@index<N>`, which is visible in the elements after N and in the second argument. Each element is typed alone, as cel-go types a variable of a policy, by compiling it alone: the type of the slot is the type of the element after the substitution, with the type variables that are still free turned to `dyn`, and an element with an error is `dyn`. The elements of the two list literals of the call are not joined by their types, so a free type variable of one element, such as the element type of `[]`, is not bound by another element, and the type map keeps `dyn` for it. The planner already plans `@index<N>` inside the block as slots; nothing changes there.

## Parsing

`CelPolicy.Parse(text, sourceName)` reads the YAML ([yaml-reader](yaml-reader.md)) and walks the root mapping as `parser.go` does, with an explicit stack for nested rules (`PolicyReader`). The model is internal (`PolicyModel`): `PolicyDocument` (name, description, imports, root rule), `PolicyRule` (id, description, semantic, variables, matches, node), `PolicyMatch` (condition, output, explanation, rule, node), `PolicyVariable` (name, expression, node), `PolicyImport`, and `PolicyString`, the text of an expression with the node it came from and its segments. Errors are `CelError.Create(InvalidPolicy, Parse, <cel-go text>, <node position>, <node length>, <key or tag>)`; all are collected and ordered by place. A YAML error stops the reading with one `InvalidYaml`; a stream without a document, or a document that is not a mapping, is `InvalidPolicy` at 1:1 with the text of cel-go (`got yaml node of kind 0, wanted mapping node`). The walk stops at 100 000 rules, matches and variables together (`the policy has more than 100000 rules, matches and variables`): aliases let a small document name a huge policy, and cel-go does not bound the walk. The reader has one more bound, a budget for text: every string it builds from a node (the name, the id, the descriptions, the condition, the output, the explanation and the expression of a variable, and the name of an import) costs its length plus its number of segments, and every error costs the length of the key or the tag that its message repeats; the sum may be at most four times the length of the document plus 65 536. A document without aliases and without errors never reaches it, since its strings are parts of the document; an alias on a long scalar used many times does, and the reader stops there with one `InvalidPolicy` (`the strings of the policy are longer than four times the document`) after the errors found before it, and builds nothing more. Without the budget the memory would be the number of uses times the size of the anchor, as the strings, their segments and the messages of the errors are built at every use.

The text of an expression follows `NewString` of cel-go. A block scalar without a tag of its own, which is the value of a key, is not the value that YAML gives: it is the lines of the document from the line after the key, as long as they start with as many spaces as the column of the key, cut by `\n` only, with their indentation and line breaks (a `\r` before `\n` stays in the text); the text is the substring of the document from the start of the first line to the end of the last, and its only segment is (0, that start, column 1). A tag of its own, `!txt` or `!!str`, makes the value the one YAML gives, as cel-go compares the style exactly and the tag adds a bit to it. A string that is not a block, quoted or plain, is the value of the scalar with the segments the YAML reader recorded. A node of another tag is `InvalidPolicy` with the text of `assertYAMLType`, and an alias is read as the node of its anchor, the same object; cel-go reads the name of the anchor there. A rule without a match, and a policy without a rule, are `InvalidPolicy` with texts of their own (cel-go fails on the empty list).

## Compilation

`Compile<T>(env, options)` (`PolicyCompiler`; partial files `Walk` and `Checks`):

1. Reject `options.SourceLocation` or `options.SourceSegments` (`ArgumentException`); keep `options.ExpectedType`.
2. Environment of the policy: `env`, or `env.ToBuilder()` with `AddAbbreviation` for each import and `Build()`; an error of the build is an error at the `name` of the import that its subject names, and the import that was rejected is left out and the policy goes on with the rest. A second environment, with the set `bindings` added when the first lacks it, checks the probe, so that a missing set is one error and not an error at each variable.
3. Parse every expression with `env.Parse(text, new CelCompileOptions { SourceSegments = segments })`. An absent condition is the literal `true` without a node.
4. Probe: a `CelExprFactory` over the document text (`VariableRewriter`). The rules are walked in document order with an explicit stack; the variables are registered in the order of the declarations (the slot is the order across the whole policy) in a scope with an undo log, and each expression is copied with `Copy(parsed, root, replace, mapOffset)`: `mapOffset` goes through the segments of the expression (`SegmentMap`), and `replace` turns a `CelSelectNode` whose operand is `CelIdentNode("variables")` into `@index<N>` of the nearest visible variable of that name declared before the copied expression (a reference forward stays `variables.b` and is an undeclared reference), unless a comprehension of the expression binds `variables`, and leaves `has(variables.name)`. The probe is `cel.@block([slot expressions], [all conditions and outputs])`; a variable whose text did not parse is the slot `dyn(null)`. One `ValidateParsed` gives the errors of the expressions, at places in the document, and the `TypeMap`.
5. The checks of the policy read the types of the probe (`compiler.go`), so they run only when every text parsed and the probe has no error: the condition is `bool`; the outputs of a rule agree with the first one by `IsAssignableType` of cel-go (`TypeRules`: a type that is `dyn`, `any` or a type parameter takes any type, a wrapper takes `null` and what it wraps, otherwise kind, name and arity are equal and the parameters assignable) in one direction or the other, and the first disagreement is the error, as in cel-go v0.33.4; `OverlappingVariable` when a registered name hides a visible one of another type. The structural checks run always: unreachable matches (a literal condition is a `CelConstantNode` of `bool`) and the limit of 100 variables and nested rules.
6. If there is any error, the result has them, ordered by place in the document, and no program.
7. Compose (next section). A composed tree with `optional.*`, `or` or `orValue` needs the set `optional`, a tree with `cel.@block` the set `bindings`; the package learns which sets the environment has by `ValidateParsed` of two small trees (`ExtensionSupport`, kept per environment instance in a `ConditionalWeakTable`). A missing set is one `MissingExtensionDependency` without a place.
8. `CompileParsed<T>(tree, new CelCompileOptions { ExpectedType = …, SourceLocation = new(sourceName, 0, 1, 1) })` in the environment of the policy. The `Expression` of the result has no source name: `CelExprFactory.Build` does not set one, and the positions of its nodes are positions of the document named by `CelPolicy.SourceName`.

`WithExplanationOutputs` copies the model: the output of each match is its explanation, and a match with an output and no explanation is left out; the imports stay, which cel-go's explanation policy loses.

## Composition

`PolicyComposer` is `composer.go` over the same parsed trees and the same factory: a rule becomes, from its last match to its first, a composition step — non-optional or optional, conditional when its condition is not the literal `true` — combined as `nonOptionalCompositionStep.combine` and `optionalCompositionStep.combine`; aggregate rules combine with `combineAggregate` (`c ? [o] : []`, `_+_`). Each expression is copied again with its own `replace` (a node occurs once in a tree). `ExpressionUnnester` then computes the heights over the tree (explicit stacks), takes the calls of height 25 or more outside comprehensions, lowest first, and moves them into new slots as `ruleUnnesterImpl` does; the height is an internal parameter, so that a test can use a small one. The root is `cel.@block([slots], rule)` when there are slots, else the rule. The nodes that composition makes have no position. Composition recurses by the depth of the rules, which the limit of 100 keeps small.

## Positions

A policy error always reports the document in `SourceLocation`. `Location` is the position in the expression for a parse error of an expression (the core reports it from `Parse`) and the position in the document for every other error: the trees of the probe and of the composed expression belong to the document text, and the errors that the package creates are created at document positions. Errors of evaluation take the place of the node in the composed tree, so they report the document too.

## Conformance suite

The suite is a suite of the runner `tests/Great.Parts.Cel.Conformance` ([conformance](conformance.md)): source `tests/cel-policy/` (a copy of `conformance/testdata` of `cel-expr/cel-policy` at a pinned commit, with `VERSION`); one case per test of `tests.yaml` of a category. The categories are the directories of the copy that have a `tests.yaml`. The environment of a category is its `config.yaml` translated to the JSON form of `CelEnvironmentJson` (by the YAML reader of the package, through `InternalsVisibleTo`), plus `optional` and `bindings`; the version of an extension set is that of the library. A case compiles `policy.yaml` once per category and evaluates the input; a success is an equal result by the rule of the cel-go runner, or, for `error_set`, a failed compilation where each string is a substring of the message of some error. The skip list, the counter and the share are those of a suite ([conformance](conformance.md)).
