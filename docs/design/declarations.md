# Declarations: variables, functions and the build of an environment

`Great.Parts.Cel.Declarations` holds the public declarations — `CelVariableDecl`, `CelFunctionDecl`, `CelOverloadDecl` and the delegates `CelFunctionImplementation` and `CelCostFunction` — and the internal form in which an environment keeps an overload with its code. `CelEnvironmentBuilder` (the facade) collects declarations as a set; `Build` checks the whole set by the rules of this page and only then creates the declaration index of [checking](checking.md). Nothing here is core: the rules decide whether an environment exists, not the value of an expression.

## Declarations

- **`CelVariableDecl`** — a name and a `CelType`. A type parameter in the type is erased to `dyn` when the environment is built: only overloads bind type parameters (see [types](types.md)). Two declarations are the same when name and type are equal.
- **`CelFunctionDecl`** — a name and at least one overload, kept in the given order; the constructor throws as its documentation says.
- **`CelOverloadDecl`** — `Global(id, parameters, result)` or `Receiver(id, receiver, parameters, result)`, whose `ParameterTypes` start with the receiver; `WithCost` returns a copy with the cost function; `Cost` is `null` without one. Two overload declarations of one function are the same when the identifier, the call style, the parameter types, the result type and the cost function (the same instance, or both none) are equal. A type parameter that occurs only in the result type stays free and checks as `dyn`.
- **`CelFunctionImplementation`** — receives the CEL values in parameter order; **`CelCostFunction`** — the cost of a call from the arguments. How evaluation calls them, charges the cost and turns exceptions into `ApplicationException` is in [evaluation](evaluation.md).

The builder takes them as follows, by the rules of the type mapping table for bindings and application functions:

| Call | Declares |
| :- | :- |
| `AddVariable<T>(name)` | a variable whose CEL type comes from `T` by the conversion rows of [values](values.md) |
| `AddVariable(name, type)`, `AddVariable(decl)` | the variable as given |
| `AddFunction(name, Func<…>)` | one global overload with the CEL types of the parameters and the result inferred from the delegate, the identifier `<name>_<type1>_…_<typeN>` (types written as in an environment description in JSON, without spaces — `isInn_string`, `sum_list<int>`, and `unix_timestamp`, `twice_duration`, since the types of time are written `timestamp` and `duration`; without parameters, the name; a .NET type outside the input rows stands in place of its CEL type, written by `Type.ToString()` — `early_System.Int128`), no cost function, and the delegate as its implementation, a typed one like that of `AddFunctionImplementation<T1, …, TResult>` below, `Build` checks included |
| `AddFunction(decl)` | the overloads of the declaration, without implementations |
| `AddFunctionImplementation(id, CelFunctionImplementation)` | an implementation that receives the values as they are |
| `AddFunctionImplementation<T1, …, TResult>(id, Func<…>)` | an implementation that converts the arguments to `T1`… by the result rows and the result back by the input rows. The CEL type of a parameter is the one that the expected-type table ([facade](facade.md), "Expected type") derives from its .NET type, as for `Compile<T>`, and must be the declared one (4011 below); for a declared `wrapper(P)` also a reference type whose type is `P` — `string` for `wrapper(string)`, `byte[]` for `wrapper(bytes)` — whose `null` is the `null` value; a refusal by the value is `ArgumentConversion`, 3024 |
| `UseContainer(container)` | the name resolution container; the empty string declares none |

Repeating a call with the same declaration adds nothing. The builder only collects; every error below comes from `Build`.

## Build

`Build` checks the whole set: the standard library version passed to the constructor, as the source `standard library v1`, and the declarations of the application, as the source `application`. Type sources are `type source '<SourceName>'`, with their own checks in [objects](objects.md); the declarations of a description in JSON are `environment JSON '<name>'` or `environment JSON`, with their place in the JSON text ([configuration](configuration.md), "Sources of declarations"); the part of extension sets adds `extension <name> v<version>`. It reports every error it finds as a `CelBuildResult` without an environment, ordered by code and then by message, ordinal, so the order of the builder calls changes neither the environment nor the errors. In a message that names two sources, the standard library comes first, otherwise the smaller source text, ordinal (`application`, then `environment JSON …`, `extension …`, `type source …`); two declarations of one source name it twice. Build errors have the stage `Build` and no location. Without errors it creates the environment: the index merges the table of the version with the overloads of the application, each wrapped into an `OverloadBinding` with the fixed cost 1 and the cost function of its declaration.

| Code | When | Message |
| :- | :- | :- |
| `InvalidFunctionName` (4015) | the name of a function of the application is not an identifier or a qualified name: segments separated by `.`, the first an `IDENT` of the language definition, the others `SELECTOR`s — so neither a reserved word first nor an operator such as `_+_` or `@in` | `function name '{name}' of {source} is not an identifier or a qualified name; operators and internal functions cannot be declared` |
| `InvalidVariableName` (4016) | the same for the name of a variable | `variable name '{name}' of {source} is not an identifier or a qualified name` |
| `TypeNotDeclared` (4008) | a type of a variable or of an overload is a .NET type outside the conversion rows, or a CEL type that nothing in the environment declares: `ObjectNamed`, and the types of later parts (`optional_type`, `decimal`); `{declarationKind}` is `variable`, `overload` or `field` (an object type in the type of a field of a description, `{name}` `<type>.<field>`), `{name}` the variable or the overload identifier, `{hint}` empty in this part; `{type}` is a CEL type in its text form, a .NET type by `Type.ToString()` (`System.Int128`), as `{clrType}` of 3015 and 3024. For a delegate form of `AddFunction` it is the first parameter type outside the input rows, in parameter order, or else the result type: one error per delegate | `{declarationKind} '{name}' has type '{type}', which no type source or extension of the environment declares{hint}` |
| `DuplicateVariable` (4000) | two different declarations of one variable name | `variable '{name}' is declared by both {source1} and {source2}` |
| `StandardLibraryConflict` (4006) | a variable named as a type identifier of the version (`google.protobuf.Timestamp` and `google.protobuf.Duration` included); a function of the application with the name, the call style and the argument count of a macro (`has` global with 1; `all`, `exists`, `exists_one`, `filter` on a receiver with 2; `map` on a receiver with 2 or 3); an overload of the application that overlaps an overload of the version of the same function | `{kind} '{name}' of {source} conflicts with standard library {version}: {detail}`, with `{kind}` `variable`, `function` or `overload`, `{version}` `v1`, `{detail}` `it is a type identifier`, `it has the form of the macro '{macro}'` or `it overlaps overload '{overloadId}'` |
| `DuplicateOverloadId` (4013) | one identifier for two overloads that are not the same, in the application or across the application and the version | `overload id '{overloadId}' is used by both {source1} and {source2}` |
| `OverlappingOverloads` (4002) | two overloads of the application of one function overlap after erasure (see [types](types.md)) | `overload '{overload1}' of {source1} overlaps overload '{overload2}' of {source2} of function '{function}'` |
| `DuplicateImplementation` (4014) | two implementations registered for one identifier, or an implementation for an overload of the version | `overload id '{overloadId}' has more than one implementation` |
| `MissingImplementation` (4007) | an overload declared with `AddFunction(decl)` that no implementation registers | `overload '{overloadId}' of function '{function}' has no implementation` |
| `UnusedImplementation` (4010) | an implementation whose identifier no overload declares | `implementation '{overloadId}' has no matching overload declaration` |
| `ImplementationSignatureMismatch` (4011) | a typed implementation — of `AddFunctionImplementation<T1, …, TResult>` or the delegate of `AddFunction(name, Func<…>)` — whose parameter count differs from the overload's; whose result type the input rows do not map to the declared result type after erasure; or a parameter whose .NET type the expected-type table ([facade](facade.md), "Expected type") does not map to the declared parameter type after erasure — `dyn` and type parameters take `CelValue` and `object`. A declared `wrapper(P)`, of a parameter or of the result, also takes a reference type whose type is `P`: `string` for `wrapper(string)`, `byte[]` for `wrapper(bytes)`, since `null` passes as a `null` reference; without it no typed delegate could take `wrapper(string)`, which no .NET type derives. A parameter type that passes is a `T` of the result rows for the declared type, so an argument that fits the declared type is passed but for a refusal by the value. So 4011: `Guid`, `short`, `sbyte`, `ushort`, `byte`, `nint`, `nuint`, `float`, `Half`, an enumeration, their `Nullable<>`, `IReadOnlyList<short>`, arrays and typed collections nested deeper than one step, such as `IReadOnlyList<IReadOnlyList<long>>` (no expected type); an `IReadOnlyList<Order>`, `Order[]` or `IList<Order>` as a parameter, `Order` a class of the application, since a nested list of a class has no expected type ("Typed nesting is one step"); `long` for `dyn`; `CelList` and `IReadOnlyList<object>` for `list(int)` (the expected type `list(dyn)`); `CelValue`, `object`, `ReadOnlyMemory<byte>` and `long` for a `wrapper(…)` (`ReadOnlyMemory<byte>` and `long` take no `null`); `DateTime` as a parameter, which the input row reads as `timestamp` but no result row gives, so no argument could fill it; `TimeSpan` or `CelDuration` for a declared `timestamp`, and `DateTimeOffset` or `CelTimestamp` for a declared `duration`. A result of `IReadOnlyList<Order>`, `Order[]` or `IList<Order>`, `Order` a class of the application, is `list(Order)` by the input rows and also fits a declared `list(dyn)`; for `list(Class)` and `list(dyn)` it builds. It builds: `IReadOnlyList<long>` and `IReadOnlyList<int>` for `list(int)`, `CelList` for `list(dyn)`, `IReadOnlyList<CelList>` for `list(list(dyn))`, `long?` for `wrapper(int)`, `string` for `wrapper(string)`, `byte[]` and `ReadOnlyMemory<byte>?` for `wrapper(bytes)`, `CelType` for `type`, `DateTimeOffset` and `CelTimestamp` for `timestamp`, `TimeSpan` and `CelDuration` for `duration` as parameter or result, the `Nullable<>` of these four for the same declared type (CEL has no wrapper of time, so a `null` result of one is `ImplementationResultMismatch` with `null_type`), and `DateTime` as a result for `timestamp`, whose kind is checked at the call ([values](values.md), "Time"). The delegate form infers the declared types by the input rows, so a .NET type outside them is 4008 there — `decimal` until its part; the collections of the application infer `list(E)` and `map(K, V)` ([values](values.md), "Collections of the application") — and the inferred overload is checked by the same rule: `AddFunction<short, bool>("small", …)` is `implementation 'small_int' does not match the signature small(int) -> bool of the overload`. A refusal by the value — `int` outside `Int32`, also an element of an `IReadOnlyList<int>` — stays `ArgumentConversion` at the call; `{signature}` is the overload in the notation of the language definition, such as `isInn(string) -> bool` or `string.isInn() -> bool` | `implementation '{overloadId}' does not match the signature {signature} of the overload` |
| `TimeZoneDatabaseConflict` (4012) | `UseTimeZones` was called with two different database objects: in either order, also through `ToBuilder`. The same object again is no conflict, `Empty` is a database like any other, and a different one is a conflict with it. The builder keeps the first database and never replaces it; however many different objects are added, `Build` reports one error | `a different time zone database is already added to the environment` |
| `ContainerConflict` (4017) | two different non-empty containers | `name resolution container '{container1}' of {source1} conflicts with container '{container2}' of {source2}` |

A conflicting pair is one error. In it the standard library comes before the application, and of two items of one source the one with the smaller overload identifier or container, ordinal, comes first, so the text does not depend on the order of the calls either. A declaration that fails a name or type check is left out of the later checks, so it produces no second error.

An overload of the application may extend a function of the standard library when it does not overlap it: `size` on an object of the application, `contains` with other argument types. Operators cannot be extended: their names fail 4015.

## Extension sets in the declaration checks

The sets of the builder go through the checks of [extensions](extensions.md#build-checks) first — 4003, 4004, 4005, 4018 — and only the surviving sets join the checks above. Their overloads are declarations like those of the standard library and the application, with the source `extension <name> v<version>` for a set of the catalog and `application` for a set of `CelExtension.Create`, which is a declaration of the application; the source of a catalog set sorts after `environment JSON` in the order of sources. What changes in each check:

| Check | With sets |
| :- | :- |
| `DuplicateOverloadId` (4013) | the identifier is unique across the standard library, every surviving set, the application and a description in JSON; the message names both sources, so `string_to_ip` declared by the application is `overload id 'string_to_ip' is used by both application and extension network v1`. A test checks that the catalog has no repeated identifier |
| `OverlappingOverloads` (4002) | two overloads of one function from different sets, or from a set and the application, that overlap after erasure; the message names both sources. Overloads of one set do not overlap by construction. The overloads of the catalog overlap neither each other nor the standard library — `reverse` of `strings` and of `lists` differ by the type of the receiver, `string` of `network` takes `net.IP` and `net.CIDR`, which no standard overload takes — and a test checks every pair of sets and each set against version 1 |
| `StandardLibraryConflict` (4006) | an overload of an application set that overlaps one of the standard library, as for an application overload. A function of the application, in a set or not, that has the name, the call style and the argument count of a macro of the **environment** — of the standard library or of a surviving set — is `function '{name}' of {source} conflicts with extension {set} v{version}: it has the form of the macro '{macro}'` for a macro of a set (`{macro}` is the name of the macro without its namespace, as in 1006: `greatest` for `math.greatest`), the existing text for a standard one: the parser expands such a call, so the function would never run |
| `InvalidFunctionName` (4015) | the names of the functions of an application set, as for the application; the catalog sets are exempt, since they declare `math.@max` and `cel.@block` |
| `MissingImplementation` (4007), `UnusedImplementation` (4010) | for an application set, against the declarations and the implementations that were given to `CelExtension.Create`: the implementations of a set belong to the set |
| `DuplicateImplementation` (4014) | also an implementation registered with `AddFunctionImplementation` for an overload of a set of the catalog, which brings its own |
| `DuplicateType` (4001) | an object type of a provider whose full name is an abstract type of a surviving set, the set named as the other source |
| `TypeNotDeclared` (4008) | a name that the catalog gives to an abstract type of a set that is not added gets the hint `; add the extension set '{set}'`; a name that a surviving set declares resolves to its abstract type ([extension-network](extension-network.md#abstract-types)) |
| `ImplementationSignatureMismatch` (4011) | the typed implementations of an application set, as for the application; a catalog set has none |

An application set is a set of declarations of the application: its overloads have `IsApplication` and everything that follows from it in [evaluation](evaluation.md#application-functions), the cost function of the overload included. A declaration that fails a name or type check is left out of the later checks, and so is a set that failed the checks of the sets.

`CelExtension.Create` itself checks only what its documentation lists — null and empty arguments — and copies its arguments: a later change of the array, the dictionary or a declaration cannot change the set. The conflicts and the other build errors are reported by `Build`, which is the only place that sees the whole environment.

## Constant arguments

Some overloads take an argument that is prepared once, when a call has it as a literal: the pattern of `matches` and `matches_string`. The layer table lets `Checking` and `Evaluation` refer to `Declarations` but not to `Library`, so the point that prepares such an argument is defined here, in three internal types, and filled in by the library:

```text
namespace Great.Parts.Cel.Declarations
internal delegate ConstantPreparation ConstantPreparer(string value, object? cache);

internal sealed class ConstantArgument
    int Index                      // the argument, the receiver counting as 0: 1 for matches and matches_string
    ConstantPreparer Prepare

internal readonly struct ConstantPreparation
    object? Prepared               // the prepared object, immutable and safe to share; null on an error
    string? Error                  // the complete text of the error, or null
```

- **On the overload.** `OverloadBinding` has `ConstantArgument? ConstantArgument`, a constructor parameter that is `null` unless the library table sets it: only `matches` and `matches_string` do. An overload of the application never has one, whatever its function is named; a call whose candidates are not all overloads with a constant argument is prepared by none ([checking](checking.md), "Constant arguments").
- **Who calls it and with what.** The checker calls `Prepare(value, cache)` in the step of type checking, once for each literal in the argument at `Index`, with the value of the literal after the escapes of CEL are read and the cache of the environment. The preparer is a method of `Library/Matches.cs`: it looks the text up in the cache of patterns, parses and builds on a miss, adds the entry, and returns the program in `Prepared`, or the text of the refusal — the same text that an evaluation of a pattern from data gives, `invalid regular expression at offset {offset}: {reason}` — in `Error`. It charges nothing and cannot throw for a pattern: every refusal is a `RegexError`.
- **Where the result is kept.** The checker puts `Prepared` in the `Reference` of the call; the planner takes it from there and gives it to the node of the call, which gives it to the implementation as `CallSite.Prepared` ([evaluation](evaluation.md), "Constant arguments"). `CallSite` also has `Cache`, the same cache, for the implementation that must prepare a pattern from data; both are `object?` and only `Library/Matches.cs` reads them.
- **The cache of the environment.** `CelEnvironment` has the field `PatternCache`, created empty by `CelEnvironmentBuilder.Build` together with the environment ([regex-engine](regex-engine.md), "The cache of patterns"), and the declaration index keeps it as an `object` that the checker and the planner hand on. `ToBuilder().Build()` makes a new environment and so a new, empty cache; the cache is no part of what makes two environments equal. No public member changes.

## The environment and `ToBuilder`

The environment keeps the declaration set it was built from. `ToBuilder` returns a new builder with the same version, variables, functions, implementations and container; `Build` on it with nothing added gives an equal environment — the same declarations, the same index order, the same results for every expression — and the earlier environment and its programs do not change. `CelStandardLibrary.V1.Version` is 1.

## Not in this part

Extension sets (4003–4005, 4018) and the `decimal` literal flag come with their parts. The time zone database and the code 4012 are in the table above and in [time zones](time-zones.md).
