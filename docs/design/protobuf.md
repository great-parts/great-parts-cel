# Protobuf: the package and the descriptions of messages

`Great.Parts.Cel.Protobuf` is the second package of the library. It turns the descriptors of `.proto` files into a `CelTypeProvider`: object types for messages, enumeration types, the known types of protobuf, proto2 extensions. Everything else — type checking of fields and literals, evaluation, cost — is done by the core through the public members of `CelObjectType`, so the package uses only the public API of `Great.Parts.Cel`; the core grants it no `InternalsVisibleTo`, and no `internal` member is opened to it. The two hooks that the core adds to `CelObjectType` for protobuf messages ([objects](objects.md#members-for-protobuf-messages)) are `protected internal virtual`, which for an assembly other than the core means `protected`: the package overrides them as an heir of the class, as any application description may, and has no access to the `internal` half. This page covers the provider, the descriptions and the reading of fields; [protobuf-messages](protobuf-messages.md) covers literals, `Any`, the JSON-like types and equality. The core side — the type `Any`, the checks and the plan of a literal, the hooks of the description — is in [checking](checking.md#message-literals-of-constructible-types), [evaluation](evaluation.md#message-literals) and [objects](objects.md#members-for-protobuf-messages); the macros of the set `protos` are in [library](library.md#the-set-protos).

The package has one namespace, `Great.Parts.Cel.Protobuf`, which is the only line of its section of `eng/layers.txt`; the folders of the project may group the files, the namespace does not change. The file names are those of this page; a change of a name does not change the page. The package is not core ([core](core.md)). It is trimmable and Native AOT compatible: it uses no reflection of its own, no `Activator`, no `MakeGenericMethod` and no `Type.GetType`; fields are read and set through `FieldDescriptor.Accessor` of `Google.Protobuf`, messages are created through `MessageDescriptor.Parser`, extensions are registered by typed objects, and a generic instantiation that the package needs — a view over one of the six key types of a map field — is written out in the code. The analyzers of the SDK make every `IL2xxx` and `IL3xxx` of the package a build error.

## The public API

The API is that of the skeleton: `CelProtobufTypesBuilder(sourceName)`, `AddFile`, `AddProtoExtension` in two forms, `Build`, and the sealed `CelProtobufTypes`, a `CelTypeProvider` whose `ObjectTypes` and `EnumTypes` are those of this page. One condition joins the documentation of `AddFile`: `ArgumentException` for a file that was not generated by `protoc` for C#, which is a file with a message that has no .NET class (`MessageDescriptor.ClrType` is `null`), such as a descriptor read from a serialized `FileDescriptorSet`. Such a file has no field accessors, so no field of it could be read. The message of the exception names the file and the first message without a class. `AddFile` checks nothing else; the other problems are reported by `Build` or, as always, by the build of the environment.

## What the builder collects

`AddFile(file)` walks the file iteratively, with a stack of its own, so that no depth of nesting reaches the thread stack:

- **Files.** The file and its dependencies, direct and indirect, each once: files are kept in a set by reference, so the same `FileDescriptor` reached again — added twice, or imported by two files — is one declaration. The files of the known types are skipped: they are always there ([below](#the-known-types)).
- **Messages.** Every message of the file with its nested messages, recursively. The synthetic entry message of a map field — the `MessageType` of a field for which `IsMap` is `true` — is no type of CEL: its field is a `map`. The known types that CEL converts ([below](#the-known-types)) are described by the package itself.
- **Enumerations.** Every enumeration of the file and of its messages, as a `CelEnumType` with the full name of the descriptor and its values by name and number; two names with one number are both constants. An enumeration constant is the identifier `<full name of the enumeration>.<value>`: `cel.expr.conformance.proto2.TestAllTypes.NestedEnum.BAR` and, for an enumeration at the top level of the package, `cel.expr.conformance.proto2.GlobalEnum.GAZ`. The scope that protobuf gives a constant — the enclosing message, not the enumeration — plays no role.
- **Extensions.** Only the extensions that were registered with `AddProtoExtension` become fields ([below](#proto2-extensions)); an extension of a file that nobody registered is not read, since reading it needs its typed object.

`Build` creates the provider. The provider is a new set of descriptions each time, built from the files and extensions added so far, so that two providers from one builder have equal descriptions that are different objects: in one environment they are a build error `DuplicateType`, as are two providers from two builders that share a file or the known types ([objects](objects.md#type-sources-of-an-environment)). The same provider added twice is one declaration. The order of the calls does not change the provider:

- the object types are in the order of their full names, ordinal, and so are the enumeration types; the `type_url` table of `Any` ([protobuf-messages](protobuf-messages.md#any)) and the type identifiers do not depend on the order either;
- the fields of a message are its fields in the order of declaration, then its registered extensions in the order of their full names, ordinal; the number of a field in `CelObjectType` is its position;
- the same extension registered twice, as the same object, is one field; two extension objects that find the same descriptor are the same field;
- the check of `Build`: an extension whose field descriptor is in none of the added files, or whose extended message is described by none of them, is `InvalidOperationException`, `the extension with the field number {number} of message {type} is declared in a file that was not added`, `{type}` the full name of the .NET message class, `typeof(TMessage).FullName`, for example `Cel.Expr.Conformance.Proto2.TestAllTypes`; all such extensions are named in one exception, sorted by name. A description that would give a message two fields with one name, which no valid set of files does, is the same exception.

The provider is immutable and shared by any number of threads and environments. The builder is not thread-safe.

## The known types

Every provider describes these seven files of `Google.Protobuf.WellKnownTypes`, whether the application added them or not: `any.proto`, `duration.proto`, `empty.proto`, `field_mask.proto`, `struct.proto`, `timestamp.proto` and `wrappers.proto`. `Empty` and `FieldMask` are messages like any other. The other types of those files are converted by CEL, so a message of them is never an object of an expression:

| Message | CEL type | Value |
| :- | :- | :- |
| `google.protobuf.Any` | `Any` | the message it contains, or what that message converts to |
| `google.protobuf.Value` | `dyn` | `null`, `double`, `string`, `bool`, `map(string, dyn)` or `list(dyn)` by its kind |
| `google.protobuf.Struct` | `map(string, dyn)` | a map view |
| `google.protobuf.ListValue` | `list(dyn)` | a list view |
| `google.protobuf.Timestamp`, `google.protobuf.Duration` | `timestamp`, `duration` | `CelTimestamp`, `CelDuration` |
| `BoolValue`, `BytesValue`, `StringValue` | `wrapper(bool)`, `wrapper(bytes)`, `wrapper(string)` | the value, or `null` for an unset field |
| `Int32Value`, `Int64Value` | `wrapper(int)` | the same |
| `UInt32Value`, `UInt64Value` | `wrapper(uint)` | the same |
| `FloatValue`, `DoubleValue` | `wrapper(double)` | the same, a float widened to `double` |

`google.protobuf.NullValue` is not in the table: it is an enumeration like any other, as in cel-go. A field of that type has the CEL type `int` and reads the number of its value, `0` for `NULL_VALUE`, so `x.null_value` is `0` and `type(x.null_value)` is `int`; only the `null_value` member of a `Value` message is read as `null`, because the kind of a `Value` decides what it reads as.

No expression holds an object of `Any`, `Value`, `Struct`, `ListValue` or a wrapper, but each of these thirteen messages has a description in the provider, because an object literal of its name is a literal of the type, and `google.protobuf.Any` must be declared by some source ([objects](objects.md#descriptions-of-well-known-types)). Such a description is made from the descriptor of its message: its fields are those of the message, with the types of this table for the fields of the known types. Its `ClrType` is a marker, a closed type `WellKnownMarker<TMessage>` of the package, never instantiated; so no .NET object belongs to the description, and the type index never finds it from a value. That is the rule of the type mapping page: a variable of the .NET type `Timestamp`, `Int32Value` or `Struct` is `TypeNotDeclared`, and a value of such a type in a `dyn` place is `TypeNotAccessible`. The descriptions of `Timestamp` and `Duration` are not made at all, since their names are type identifiers of the standard library; a literal `google.protobuf.Timestamp{…}` is `NotAType`, as it is without the package, and the application writes `timestamp(…)`.

Two providers each describe the known types, so two providers in one environment are `DuplicateType`: the files of the known types cannot be shared between providers, and one provider per environment is the rule for them. This is the rule of the type mapping page, which a fingerprint of the descriptions may relax in a later version.

## Message descriptions

`MessageType` derives from `CelObjectType` and holds one `FieldPlan` per field, in an array indexed by the field number of CEL. `GetField(instance, number)` and `HasField(instance, number)` read `plans[number]`: no lookup by name, no reflection, no dictionary on the path. A `FieldPlan` holds, decided once when the description is made:

- the `FieldDescriptor` and its `IFieldAccessor` (for an extension, three delegates made when it was registered);
- the kind of the field, which picks the conversion in a `switch`: the scalar kinds, `enum`, message, one of the known types, `repeated` with the kind of its element, `map` with the kinds of its key and value;
- how presence is decided ([below](#presence)) and whether the field is a member of a `oneof`;
- the `CelType` of the field and, for a field of a known type, the converters that reading and writing need.

The type in `CelObjectField` is the CEL type of the value that reading gives:

| Field of protobuf | CEL type |
| :- | :- |
| `int32`, `sint32`, `sfixed32`, `int64`, `sint64`, `sfixed64` | `int` |
| `uint32`, `fixed32`, `uint64`, `fixed64` | `uint` |
| `float`, `double` | `double` |
| `bool`, `string`, `bytes` | `bool`, `string`, `bytes` |
| enumeration, `google.protobuf.NullValue` included | `int` |
| message `M`, not a known type | the object type `M` |
| a known type | the type of the table above: `Any`, `dyn`, `map(string, dyn)`, `list(dyn)`, `timestamp`, `duration`, the wrapper types |
| `repeated T` | `list(` the type of `T` `)` |
| `map<K, V>` | `map(` the type of `K`, the type of `V` `)` |
| extension | the type of its field by these rows; the name is the full name of the extension |

`group` fields of proto2, which protobuf deprecates and `Google.Protobuf` reads as messages, are messages like the others.

## Reading a field

`GetField` takes the value from the message with `IFieldAccessor.GetValue`, which gives an `object`, and converts it by the kind of the field. A read boxes a scalar once, 24 bytes, inside the unit of the field selection ([evaluation](evaluation.md#fields-of-objects)); nothing else is copied.

| Kind | Value |
| :- | :- |
| `int32` … `sfixed64` | `CelValue.FromInt64` of the number |
| `uint32` … `fixed64` | `CelValue.FromUInt64` |
| `float` | the `float` widened to `double`: `FloatValue{value: 1.333}` read back is 1.3329999446868896, not 1.333 |
| `double`, `bool`, `string` | as they are |
| `bytes` | `CelValue.FromBytes` of `ByteString.Memory`: the bytes of the message, not copied |
| enumeration | `CelValue.FromInt64` of the number, whether the enumeration declares it or not; for `google.protobuf.NullValue` too: `NULL_VALUE` reads `0` |
| message `M` | the instance of the field as a bare object (`CelObjectType.FromInstance`); the place rule of [objects](objects.md#object-values) pairs it with the description of `M` when a field has the object type. A message field that is not set reads as a new empty message of that class, shared by the provider and never changed; the language definition asks for the empty message, and `has()` still tells the two apart |
| `Any` | the unpacked content, [protobuf-messages](protobuf-messages.md#any); an unset field reads `null`, as in cel-go and in the cases of cel-spec, and is not unpacked. A field that is set is unpacked even when its type URL is empty, which is `InvalidAny` |
| `Value` | the kind that is set; a `Value` with no kind and an unset field read `null` |
| `Struct` | a map view over `Struct.Fields`, in the order of insertion; an unset field is the empty map |
| `ListValue` | a list view over `ListValue.Values`; an unset field is the empty list |
| `Timestamp` | `CelTimestamp`; an unset field reads the zero value, `1970-01-01T00:00:00Z`, as in cel-go: a `Timestamp` is a message of two numbers and not a wrapper, so `null` is not its unset value |
| `Duration` | `CelDuration`; an unset field reads the zero value, `0s` |
| wrapper | the primitive value of the wrapper; an unset field is `null`; a wrapper that is set and holds the default reads the default: `Int32Value{}` is `0` |
| `repeated` | a `CelList` view |
| `map` | a `CelMap` view |

- **`Timestamp` and `Duration`.** A `Timestamp` with `nanos` outside 0 to 999 999 999, or with `seconds` outside the range of `CelTimestamp` (0001-01-01T00:00:00Z to 9999-12-31T23:59:59.999999999Z), reads as the error value `ConversionRange` with the text `{value} is out of the range of timestamp`, `{value}` the `seconds` or, when those are right, the `nanos`, in decimal. A `Duration` is the nanoseconds `seconds · 10⁹ + nanos`; a total outside the range of `long`, or `seconds` and `nanos` of different signs, or `nanos` beyond ±999 999 999, gives `ConversionRange` with `{value} is out of the range of duration`, `{value}` the `nanos` when `nanos` is beyond ±999 999 999 or of a different sign than `seconds`, otherwise (the total outside `long`) the `seconds`; the `nanos` is checked first, the opposite of `Timestamp`. The error is `CelObjectType.FieldError(number, ConversionRange, text)`.
- **`repeated`.** `CelList.CreateView` over a read-only list of objects that wraps the non-generic `IList` of the `RepeatedField<T>`; an element is converted by the kind of the element each time it is read, with a converter made once for the field. The view reflects the field: the application must not change a message while an evaluation reads it. A list of messages gives bare objects, a list of `Any` unpacks each element when it is read.
- **`map`.** `CelMap.CreateView` with `keepSourceOrder` set, over a read-only dictionary that wraps the non-generic `IDictionary` of the `MapField<K, V>`. `MapField` enumerates in the order of insertion, so the order of a `map` is the order of insertion, as the type mapping page says. The key type of the wrapper is one of the six that protobuf allows — `int`, `long`, `uint`, `ulong`, `bool`, `string` — each instantiated in the code, so no generic is made at run time. A value is converted like the element of a list.
- **`oneof`.** The members of a `oneof` are fields of their own; a member that is not the one set reads as the default of its type, as every unset field of proto3 does.
- **Errors.** Reading gives an error value only for `Timestamp`, `Duration` and `Any`, and for the elements and values of the `repeated` and `map` fields of those types; every other field reads without an error. An error of an element of a `repeated` field or of a value of a `map` field — `InvalidAny` of an `Any` that does not unpack, `ConversionRange` of a time — is made when the element is read, not when the field is, so the field and the other elements read as usual; its place is the node that read the element, the rule of the table of errors of [evaluation](evaluation.md#errors-as-values) (`InvalidAny`). An exception that the accessor throws is turned by evaluation into `ApplicationException`, like any exception of code that a description calls.

An element of a `repeated` field and a value of a `map` field are converted by the row of their kind, as the value of a single field is; the rule of the unset message belongs to a field, since a container of generated code holds no `null` element.

### Cost of a read

A field selection costs 1 ([evaluation](evaluation.md#fields-of-objects)), whatever the field holds, and the description adds nothing for every kind but `Any`: a view, a wrapper or a message is O(1) to make. For a field of the type `Any` the description tells the core, through `FieldReadCost`, the units of the unpack, so they are charged before the read and before the parse: `1 + ⌈(U + B)/10⌉`, where U is the length of the type URL in UTF-16 units and B the bytes of the content; for a `repeated` field of `Any` or a `map` field with `Any` values the sum of those units over all elements, found in one pass, since the elements are unpacked when the view is read and the core cannot see which will be. An unset field of `Any` adds nothing: it reads `null` and is not unpacked, so the selection costs its unit alone. `has()` charges 1 only. The memory of a read stays within 64 bytes per unit: the view of a collection, the box of a scalar and the converter of the element are one object each, created inside the unit, and an unpack allocates what its units pay for ([protobuf-messages](protobuf-messages.md#any)).

## Presence

`HasField(instance, number)` follows the language definition, "Field Selection", in this order, by the kind of the field:

| Field | `has()` is true when |
| :- | :- |
| extension, single | `HasExtension` of the typed object; for a repeated extension, when the list is not empty |
| `repeated`, `map` | the container is not empty |
| a member of a `oneof` — real, not the synthetic one of a proto3 `optional` | this member is the one set, also when its value is the default |
| any field for which `FieldDescriptor.HasPresence` is true — every message field, every field of proto2, a proto3 `optional` field | `IFieldAccessor.HasValue`: the field has been set, also to the default |
| any other field — a proto3 scalar or enumeration without `optional` | the value differs from the default of its type: not 0, not `false`, not the empty string or bytes; a `float` or `double` is the default only when its bit pattern is that of `+0.0`, so `-0.0` and a NaN are present |

So `has(m.single_int32)` of proto2 is true after `single_int32: 0` and false for a message without it; of proto3 it is false in both. An unset `Any`, `Value`, `Struct`, wrapper, `Timestamp` or `Duration` field is not present, and a wrapper that is set to the default is. A proto3 `optional` scalar is present after it is set to the default. The property `FieldDescriptor.HasPresence` is a public property of `Google.Protobuf`; the package relies on it for the proto3 `optional` fields and the extensions, and a test of the package checks that it exists in the version of `Google.Protobuf` that the package uses and gives the answers of the table for the test messages ([tests](tests.md#tests-of-the-protobuf-package)).

A field that the message does not have is `no_such_field`: the checker reports `NoSuchField` at the selection; without type checking evaluation reports `EvalNoSuchField` ([checking](checking.md#rules-per-node), [evaluation](evaluation.md#nodes)). A name with dots — an extension — is selected in backquotes, `` m.`pkg.ext` ``, or through `proto.getExt` and `proto.hasExt` ([library](library.md#the-set-protos)).

## proto2 extensions

`AddProtoExtension<TMessage, TValue>(Extension<TMessage, TValue>)` and the overload for `RepeatedExtension<TMessage, TValue>` register a typed extension object of the generated code, and nothing else. At `Build`:

1. The field descriptor of the extension is found among the extensions of the added files that extend a message of the added files: for each message type the provider describes, `ExtensionCollection.GetExtensionsInDeclarationOrder(messageDescriptor)` of the extension collections of every added file and, recursively, of every added message gives the candidates, and the one whose `FieldDescriptor.Extension` is the registered object, by reference, is the field. The generated code gives each descriptor its extension object, so no reflection finds the pair. No candidate: the exception of `Build` above.
2. The field is added to the description of the extended message, after its own fields, with the full name of the extension as its name — `cel.expr.conformance.proto2.int32_ext` for an extension declared at the top level of the file and `cel.expr.conformance.proto2.Proto2ExtensionScopedMessage.int64_ext` for one declared inside a message — and the CEL type of its descriptor by the rows above: `int`, the enumeration as `int`, a message as an object, `repeated` as a `list`.
3. Three delegates are made by the generic method that received the object, so they know `TMessage` and `TValue` without reflection: `get`, `((IExtendableMessage<TMessage>)message).GetExtension(extension)` boxed to `object?` (for a repeated extension the `RepeatedField<TValue>`, or `null` for none); `has`, `HasExtension(extension)`, or for a repeated extension a non-empty list; `set`, `SetExtension(extension, (TValue)value)`, or for a repeated one `GetOrInitializeExtension(extension)` and an `Add` of each element. They run in the exception boundary of the evaluation like `GetField`.
4. Reading, presence and writing then go through the same conversion by the kind as an ordinary field, since the delegates give and take the boxed value the accessor of an ordinary field would.

The provider reads an extension from the instance it is given. A message that the application parsed without the extension in its registry holds the extension among its unknown fields, and `GetExtension` does not read it: the application parses with the registry that holds the objects it registers with the builder. A message that the package parses itself — the content of an `Any` — is parsed with an `ExtensionRegistry` that holds every registered object, in the order of their full names, so the registered extensions are in it ([protobuf-messages](protobuf-messages.md#any)).

## Projects and test messages

The package has no `.proto` of its own and neither have its tests. The messages of the pinned cel-spec — `proto2/test_all_types.proto`, `proto3/test_all_types.proto`, `proto2/test_all_types_extensions.proto` — have every kind a test needs: all the scalars, `bytes`, enumerations (nested and at the top level), `repeated` and `map` of every element type, a `oneof`, proto3 `optional` scalars, enumerations and `NullValue`, `Any`, `Struct`, `Value`, `ListValue`, the nine wrappers, `Timestamp`, `Duration`, `Empty`, `FieldMask`, and proto2 extensions of both scopes with a scalar, an enumeration, a message and a `repeated` message. The three test projects compile them into C# classes with `Protobuf Include` and `GrpcServices="None"`, namespaces `Cel.Expr.Conformance.Proto2` and `Cel.Expr.Conformance.Proto3`:

| Project | Compiles | References the package | Why |
| :- | :- | :- | :- |
| `tests/Great.Parts.Cel.Tests` | the three test messages | yes | the examples and the tests of the package; the project is published under Native AOT with the package |
| `tests/Great.Parts.Cel.Conformance` | the three test messages, besides `simple.proto` and its imports | yes | the runner builds its provider from them; the project is published under Native AOT |
| `tests/Great.Parts.Cel.Properties` | the three test messages | yes | the property of the order of builder calls takes providers |

The tests of the package are in `tests/Great.Parts.Cel.Tests/Protobuf/`, a folder of the existing project: a separate test project would need a project file, a line of `eng/layers.txt`, a place in the solution and in the Native AOT publishes, and it would give nothing the folder lacks. Each project has its own compiled copy of the classes: three assemblies, three sets of types, never mixed. `eng/difftest` needs no message class: the library side of its stand adds a provider with the known types only ([eng-difftest](eng-difftest.md#provider-of-protobuf-on-the-library-side)).

The package depends on `Great.Parts.Cel` and `Google.Protobuf` only, as the build checks of the packages require; its project file and its lines in `eng/layers.txt` and `eng/packages/` do not change. A `Native AOT` publication of `Great.Parts.Cel.Tests` and `Great.Parts.Cel.Conformance` with the package, `InvariantGlobalization=true`, gives no `IL2xxx` or `IL3xxx` from `Great.Parts.Cel.Protobuf`; the number of tests of each project under Native AOT equals that of the JIT run, and the cases of protobuf, which run as part of one test of the runner, give the same count of passed cases in both modes ([conformance](conformance.md#environment-of-the-cases)).

## Changes to the text of the skeleton

The XML documentation of the skeleton changes with the parts that implement it:

- `CelProtobufTypes`: the sentence on equality names what [protobuf-messages](protobuf-messages.md#equality) does — the descriptors and the set fields by CEL equality, a NaN not equal to itself, `Any` unpacked first, and the bytes of the packed message when it cannot be unpacked — and no longer says that unknown fields are compared by their bytes: the generated classes give no access to them.
- `CelProtobufTypesBuilder.AddFile`: the `ArgumentException` above.
- `CelObjectType.CreateInstance`: the default throws `NotSupportedException`, as its documentation says; the skeleton throws `NotImplementedException`.
- `CelObjectType.FieldError`: for `InvalidAny`, as for `ConversionRange`, the argument `detail` is the whole text; the package builds it from the template of the code ([objects](objects.md#members-for-protobuf-messages)).
