# Evaluation: planner and evaluator

`Great.Parts.Cel.Evaluation` turns a checked expression into a plan once, at compilation, and evaluates the plan on bindings at each call. A plan is a tree of immutable nodes; the state of one evaluation lives in a frame created for that call. There is no compilation to expression trees, byte code or closures.

| File | Content |
| :- | :- |
| `src/Great.Parts.Cel/Evaluation/Planner.cs` | plans a checked expression, or a parsed one without type checking |
| `src/Great.Parts.Cel/Evaluation/Plan.cs` | the root node, the slots, the line table; `Evaluate(bindings, costLimit, cancellationToken)` |
| `src/Great.Parts.Cel/Evaluation/PlanNode.cs` and one file per node class | the nodes |
| `src/Great.Parts.Cel/Evaluation/Frame.cs` | the state of one evaluation |
| `src/Great.Parts.Cel/Evaluation/CostLimitException.cs` | the internal signal of an exceeded cost limit |
| `src/Great.Parts.Cel/Evaluation/EvaluationErrors.cs` | the messages of the evaluation errors |
| `src/Great.Parts.Cel/Values/IEvaluationMeter.cs` | `Charge(ulong units)` and `Event()`: how library implementations and value rules reach the frame; it lives in `Values`, the lowest namespace that needs it |

## Plan nodes

`PlanNode` is abstract: it keeps the offset of its syntax node and has one method, `CelValue Evaluate(Frame frame)`. A node never changes after planning, so one plan serves any number of threads at once. Every node charges its cost before its own operation, after its children; the costs are those of the cost table of the documentation.

| Node | Planned from | Cost |
| :- | :- | :- |
| `ConstantPlanNode` | a literal; a type identifier, an object type of the application included, whose type value the planner takes from the declaration index; an enumeration constant; a call of `timestamp` or `duration` on a string literal ([Time](#time)) | literal 0; type identifier and constant 1, as a name read; a folded time constant ([Time](#time)) the units of the call it replaces |
| `VariablePlanNode` | an identifier or a selection that names a declared variable | 1; at the first read also the check of the binding ([values](values.md), "Fits a type") |
| `LocalPlanNode` | an iteration variable or the accumulator of a comprehension | 1; see comprehensions for the reads that cost 0 |
| `FieldPlanNode` | `e.f` and `has(e.f)` whose operand has an object type, with the description and the field number of the reference map | 1 |
| `SelectPlanNode` | any other selection `e.f` that names no declaration; `has(e.f)` | 1 + ⌈L/10⌉ on a map, L the length of `f`; on a JSON object the key lookup of the cost table; 1 otherwise |
| `CallPlanNode`, `DispatchPlanNode` | a call with one candidate; with several, or none | the cost of the overload |
| `AndPlanNode`, `OrPlanNode` | a chain of `_&&_` or of `_\|\|_` calls | 0 beyond the operands |
| `ConditionalPlanNode` | `_?_:_` | 0 beyond the operands |
| `NotStrictlyFalsePlanNode` | `@not_strictly_false` | 0 |
| `ListPlanNode` | a list literal | 1 + n for n elements |
| `MapPlanNode` | a map literal | 1 + 2n for n entries, a key and a value each, and ⌈L/10⌉ for each string key of length L |
| `ComprehensionPlanNode` | a comprehension | 1 per executed step |
| `AppendPlanNode` | the step `@result + [e]` of `map` and `filter` | 1 per added element |

The planner gives each distinct variable of the expression a slot, and each comprehension two more, for its iteration variable and its accumulator; every reference reads its slot. The parser builds chains of `&&` and `||` as balanced trees; the planner flattens each into one node with the operands in the order of the text and the position of the outermost call. An index `e[i]` is the call `_[_]` of the library.

## Nodes

**Variable.** The first read of a slot looks the name up in the bindings, checks the value with `ValueTypeRules.Fits` against the declared type of the variable at any depth ([values](values.md)) and keeps the value, or the error `BindingTypeMismatch`; later reads take it from the slot and check nothing. No value is `Unbound`. So a list of strings bound to a variable of type `list(int)` is `BindingTypeMismatch` at the first read of the variable, whatever the expression does with it — `size(x)` included — and never reaches an overload or the result conversion. A variable of an object type applies the place rule of [objects](objects.md) at the first read, with and without type checking: a bare instance that belongs to the type is kept, or paired with the description of the type, in the slot.

**Selection and presence.** The operand comes first; an error value is the result. On a map, `e.f` is the value of the string key `f`, and no such key is `EvalNoSuchField`; `has(e.f)` is whether the key is present; a JSON object uses its counting lookup ([values](values.md), "`JsonElement`"). On an object value the field is found by name in the description of the value ([objects](objects.md)) at each evaluation, then read as below; no such field is `EvalNoSuchField` with the full name of the type, for `has()` too (the language definition, "Field Selection"). Any other value, which only an operand of static type `dyn` or evaluation without type checking can give, is `FieldSelectionNotSupported` for both, after the constant unit only. For `has()` the language definition requires the error ("Field Selection", case 5). cel-go v0.32.0 returns `false` only without `EnableErrorOnBadPresenceTest`, which the oracle and the cel-go conformance runner set; with it both sides fail, so there is no difference.

**`&&` and `||`.** The operands are evaluated from left to right, and the first operand that decides the result — `false` for `&&`, `true` for `||` — is the result, without evaluating the rest. Otherwise the first operand that is an error value, or that is not a `bool` and so gives `EvalNoMatchingOverload` with all operand types of the chain (`no such overload: _&&_(int, bool)`), is the result; when no operand decides it and none fails, the result is `true` for `&&` and `false` for `||`. So `x || true` is `true` and `x && false` is `false` even when `x` is unbound.

**`?:`.** The condition first: `true` evaluates only the second operand, `false` only the third; an error value is the result; another kind is `EvalNoMatchingOverload` with the type of the condition (`no such overload: _?_:_(int)`).

**`@not_strictly_false`.** A `bool` operand is the result; any other value, an error included, is `true`.

## Fields of objects

`FieldPlanNode` holds the description `T` and the field number that type checking recorded, so it reads a field without looking up a name and without converting the rest of the object. It evaluates the operand, then:

1. An error value is the result. An object value whose description ([objects](objects.md)) is `T` — a pair of `T`, or a bare instance that belongs to `T`, by an instance test of the `ClrType` or the carrier class, not by the type index — is read with the bound number. Any other value is taken as by `SelectPlanNode`, by name: a static type is no guarantee of the value ([values](values.md), "Fits a type"), so `([deal] + dyn([other]))[1].amount` reads `amount` of whatever `other` is, or fails as there.
2. It charges 1 unit, counts one event (see cancellation), since it calls code of the application, then calls `GetField(instance, number)` for `e.f` or `HasField(instance, number)` for `has(e.f)` inside the exception boundary of "Application functions": an exception other than `OutOfMemoryException`, the internal `CostLimitException` and the `OperationCanceledException` of the canceled token is `ApplicationException` with the callee `field '{field}' of type '{type}'` or `the presence test of field '{field}' of type '{type}'`.
3. The value of a field enters by the place rule of [objects](objects.md) when the field has an object type. For a type described at run time `GetField` gives `FieldNotSet` and `FieldTypeMismatch` itself ([objects](objects.md), "Types described at run time"). An error value without a position — from a field, a converter or an element of application data — gets the position of the selection.

`SelectPlanNode` on an object value does steps 2 and 3 with the number it found. Neither node checks the value of a field at depth: the elements of a list field are checked where an operation reads them.

## Comprehensions

`ComprehensionPlanNode` evaluates the range first: an error value is the result; a list gives its elements in order and a map its keys in the order of the map; another value is `EvalInvalidComprehensionRange` at the range. The node then evaluates the accumulator initializer into the accumulator slot and, for each element, puts it into the slot of the iteration variable, evaluates the loop condition and stops when the condition is `false`; otherwise it counts an event (see cancellation), charges 1 unit and evaluates the step into the accumulator slot. The result is evaluated after the loop. There is no early exit on an error value: the accumulator holds whatever the step gives, as the expansion of the macro says (see [syntax](syntax.md), macros), so `all` and `exists` absorb errors by the rules of `&&` and `||`, and `exists_one`, `map` and `filter` keep them.

The standard macros expand with the hidden accumulator `@result`, which no text can write, so the planner recognizes their parts. The cost of a standard macro is the row of the cost table: the range, the predicate and the transform — the expressions the author wrote — are charged by their rows; each executed step costs 1; `[]` as the initializer of `map` and `filter` is a list literal of 1 unit, the other initializers are literals of 0; each element that `map` or `filter` adds costs 1. Everything else the expansion adds — the reads of `@result`, the loop condition with `@not_strictly_false` and `!`, the `&&`, `||` and `?:` of the step, the `+ 1` of `exists_one`, the result, and the read of the iteration variable that `filter` adds to its list — is part of the step and costs nothing.

The step `@result + [e]` of `map` and `filter` becomes an `AppendPlanNode`: during the loop the accumulator slot holds a list builder, and the node evaluates `e` and appends its value, without the one-element list and the concatenation that the expansion writes. It is strict like the concatenation it replaces: an error value of `e` becomes the accumulator, and an accumulator that is an error value stays. The read of `@result` in the result turns the builder into a list over an array filled once ([values](values.md)). The array of the builder grows by doubling from 4 elements up to the size of the range, as elements are added, so that the bytes follow the units charged and a limit that stops the loop stops the allocation. So `map` and `filter` take linear time, and the memory is charged as the elements are added.

## Calls

Type checking records the candidates of each call in the reference map (see [checking](checking.md)); each candidate is an `OverloadBinding` with its implementation and cost (see [library](library.md)).

1. Calls of `_&&_`, `_||_`, `_?_:_` and `@not_strictly_false`, whose overloads have no implementation, become the nodes above. Any other call with one candidate becomes a `CallPlanNode`, a call with several candidates a `DispatchPlanNode` with all of them. A `_[_]` whose operand has the static type `dyn` is a `DispatchPlanNode` with `index_list` and `index_map`, in the order of the library, whatever candidates type checking kept: cel-go v0.32.0 indexes by the kind of the operand at run time, so `x[0u]` with `x` of type `dyn` bound to `[7]` is 7, as without type checking, though a `uint` key leaves the check only `index_map`.
2. Both nodes evaluate the arguments from left to right. Calls are strict: the first argument that is an error value is the value of the call, and no implementation runs.
3. The planner marks the arguments that the node checks at depth with `OverloadBinding.Matches` before the implementation runs ([values](values.md), "Fits a type"; `Matches` checks the top level of every argument, which costs nothing); a mismatch is `EvalNoMatchingOverload` at the call.
   - For an overload of the application every argument is marked, whatever its static type: application code gets only values that fit the declared parameter types, type parameters as `dyn`.
   - For an overload of the library an argument is marked when its static type after the substitution does not cover the parameter type: it is `dyn` or a wrapper, or it has `dyn` or a wrapper inside `list` or `map` where the parameter type has another type, as `list(dyn)` for `list(int)`. A `CallPlanNode` whose arguments are all unmarked calls the implementation directly.
   - An unmarked argument may still hold a value that does not fit its static type: a static type is no guarantee ([values](values.md), "Fits a type"), so `([1] + y)[1]` with `y` = `dyn(['a'])` is an `int` that holds `'a'`. The implementation meets a kind it does not take and returns `EvalNoMatchingOverload` itself ([library](library.md), "Implementations and cost"): `([1] + y)[1] + 1` is `no such overload: _+_(string, int)`, the outcome of cel-go v0.32.0, whose overloads guard the kinds of their arguments at run time.
4. A `DispatchPlanNode` calls the first candidate, in the order of the reference map, that `Matches` the values; none is `EvalNoMatchingOverload` at the call. For each candidate the planner marks the arguments as in step 3; `Matches` checks the top level of all of them and the depth of the marked ones only, so an argument of static type `list(int)` costs nothing against `list(int)`, and a value of another kind under a static type chooses no candidate.
5. With a cost limit the node charges `FixedCost` plus `ArgumentCost` of the arguments before the implementation runs, after the checks of step 3 or 4, which charge what they descend into. An implementation may charge more through `CallSite.Charge` while it runs: equality charges pair by pair, a conversion to text the length of the text before creating it.

So evaluation calls only an overload that type checking accepted, or the other index overload of a `dyn` operand.

## Application functions

A call of an overload of the application, `OverloadBinding.IsApplication`, goes in this order after its arguments pass the checks of step 3 of "Calls":

1. it counts one event (see cancellation);
2. with a cost limit, it calls the `CelCostFunction` of the overload and charges 1 plus its value; when the total exceeds the limit, the implementation is not called;
3. it calls the implementation: the delegate, through the wrapper of the builder when the delegate is typed; the wrapper converts the arguments by the result rows of the type mapping table (a refusal is `ArgumentConversion`, by the value only: a parameter type whose expected type is not the declared one is a build error, [declarations](declarations.md), 4011; a copy is charged first: a list of n elements 1 + n, a map of n pairs 1 + 2n and ⌈L/10⌉ for each string key of length L, as a created map, because the copy hashes each string key, the term of a key charged before the key is put into the copy; and each `bytes` value of length L put into a `byte[]` — the rows `byte[]` and `object`, also as an element or a value of a copy — 1 + ⌈L/10⌉; a copy allocates at most 64 bytes per unit it charges, so an empty map is one shared instance and a map of one pair is no `Dictionary`, and the memory of a map copy does not depend on the length of its keys; what a lazy view creates when the implementation reads it is memory of the implementation) and the result back by the input rows ([values](values.md)). Whether an argument is a lazy view or a copy follows from the pair of the declared parameter type and the .NET parameter type, by the pairs of [facade](facade.md), "Result conversion": the checks of step 3 of "Calls" made the argument fit the declared parameter type at every depth, so a lazy view of a pair that cannot fail does not fail. For `list(int)`, `IReadOnlyList<long>` is a lazy view, not charged; `IReadOnlyList<int>` a copy, charged 1 + n, whose element outside `Int32` is `ArgumentConversion`; for `bytes`, `ReadOnlyMemory<byte>` is not charged and `byte[]` is a copy;
4. an error value returned is the value of the call. Otherwise the value must fit, by `ValueTypeRules.Fits` at any depth and with the meter, the declared result type of the overload with its type parameters as `dyn`, or the call is `ImplementationResultMismatch`. The type of the call that type checking recorded is not checked: a type parameter bound by the arguments may stand for a `dyn` value, and `first(list(A)) -> A` on `dyn(['a']) + [1]` rightly returns `'a'` though the call has the type `int`. A result type `dyn` checks nothing. A result whose CEL type the input row of the typed delegate already gives — `Func<long>` for `int` — fits by construction and is not checked, except a .NET `null`: the input rows turn a `null` `string`, `byte[]`, `CelList` and `CelMap` into the `null` value, which fits none of `string`, `bytes`, `list(dyn)` and `map(dyn, dyn)`. Such a result is checked at the top level only, which costs nothing, and `AddFunction<string, string?>` whose delegate returns `null` is `ImplementationResultMismatch` with `null_type`, as is a `Func<CelList>` that returns `null` for `list(dyn)`. A `string` or `byte[]` result for a declared `wrapper(string)` or `wrapper(bytes)` ([declarations](declarations.md), 4011) fits with `null` as well, so it is not checked. Evaluation without type checking checks the same.

**Results that are copied.** A typed delegate whose .NET result type is `IReadOnlySet<T>` or `ISet<T>`, or another `IReadOnlyCollection<T>` without an index (`Queue<T>`, `Stack<T>`, `LinkedList<T>`), returns a collection that the input rows copy ([values](values.md), "Input rows"). The copy is part of step 3, after the implementation returns and before step 4:

- **Set.** A first pass over the source, which converts nothing, gives n and Lmax, the greatest length of the `string` and `bytes` elements (0 without them). With a cost limit the wrapper then charges the row of the cost table for a set read as a list, 1 + c · n · ⌈log₂(n + 1)⌉ with c = 1 + ⌈2 · Lmax/10⌉, which is 1 for numbers and `bool`. Only then does it convert the elements into an array of n values and sort it in place by `OrderingRules`, strings by code points. Every refusal of `CelList.CreateSorted` — `null`, an element that converts to an error value, two kinds, a kind without an order, a NaN, two elements equal in CEL — is one error value, after the charge: `InvalidArgument` (3008) `invalid argument to '{overloadId}': a result set whose elements CEL cannot sort`, at the call. The text names no element, so it does not depend on the order of enumeration of the set, which depends on hash codes.
- **Collection without an index.** With a cost limit the wrapper charges 1 + n, then copies the elements in the order of enumeration; an element that converts to an error value is kept as an element, as by `CelList.CreateCopy`.

The copy holds n values of 32 bytes, and the sort runs in place, so the memory stays within B per unit of the row. The result fits its declared type by construction, unless its element type is `dyn` (`ISet<object>`), whose check costs nothing at the top level (step 4).

Steps 2 and 3 run inside the exception boundary: an exception becomes `ApplicationException`, which keeps it in `CelError.Exception`. It passes through only `OutOfMemoryException`, the internal `CostLimitException` and an `OperationCanceledException` whose token is the canceled token of the evaluation.

## Constant arguments

A call whose `Reference` carries a prepared object ([checking](checking.md), "Constant arguments") is planned with it: the node of the call, `CallPlanNode`, or `DispatchPlanNode` when the candidates are several, keeps the prepared object in a field and gives it, with the cache of patterns of the environment, to the `CallSite` it makes for each evaluation, as `Prepared` and `Cache` ([declarations](declarations.md), "Constant arguments"). The plan holds the cache, which it takes from the declaration index when it is planned. The prepared object is immutable and shared by every evaluation and thread; the cache can evict the entry it came from and the plan still holds the program. The argument itself is planned as any literal, a `ConstantPlanNode` of cost 0, and evaluated in its place among the arguments, so the order of evaluation, strictness and the kind check of `Matches` are those of any call; the implementation uses `Prepared` and does not read the literal again.

- **A literal pattern that is prepared** costs the match alone ([library](library.md)): the parse and the build were made at compilation. Its refusal never reaches evaluation, since the compilation failed with `InvalidRegex` and there is no plan.
- **A pattern that is not a literal** — a variable, `dyn('(')`, `string('(')`, a concatenation, a `?:`, an element of a list or of a map, any call — has no prepared object. The implementation parses it after the operands have been evaluated and an error value among them has been returned, looks it up in the cache and builds it, and the refusal is `EvalInvalidRegex` at the call, never earlier: a branch that is not evaluated gives none, `false && matches('a', p)` with `p` bound to `(` is `false`, and `matches('a', p) || true` is `true` since `||` takes the error as it takes any.
- **The place** of `EvalInvalidRegex` is the call: for the form from a receiver too, the `(` after the name, which is the position the planner gives to every call node; in a macro, the `(` in the text, whichever element it is evaluated for.
- **Events and cancellation.** A call of `matches` is no event of the frame: the steps of the engine are not counted, and a cancellation is seen at the next event after the call. The work of one call is what its cost pays for.

The preparation is a property of the checked plan. It is not folded from a value: nothing that is not a string literal is prepared, so the same expression gives the same class of outcome with and without a cache, in any environment.

## Frame

`CelValue Plan.Evaluate(IReadOnlyDictionary<string, CelValue> bindings, ulong? costLimit, CancellationToken cancellationToken)` creates a `Frame` for one evaluation on one thread, evaluates the root and returns its value or error value. The bindings are a read-only dictionary by name: the facade passes the one inside `CelBindings` (see [facade](facade.md)); the internal `CelProgram<T>.Plan` gives the plan of a program to the tests. The frame holds:

- the slots of the variables, with a filled flag each, and the slots of the comprehensions;
- the argument stack, which calls use instead of an array per call; a call pushes its argument values and gives the implementation a span over them;
- the meter, which implements `IEvaluationMeter`: the remaining units and the limit, only when the options set a limit; the event counter, only when the token can be canceled;
- the offset of the node whose own operation runs, which each node records before it: the place of `CostLimitExceeded` and `InternalError`.

`Plan.Evaluate` is two internal steps, which the property of cost and memory (see [tests](tests.md), "Properties of evaluation") calls one by one: `Frame CreateFrame(IReadOnlyDictionary<string, CelValue> bindings, ulong? costLimit, CancellationToken cancellationToken)` allocates the frame with its slots, argument stack and meter, and `CelValue Run(Frame frame)` evaluates the root inside the handler of "Stack and internal errors", turning `CostLimitException` into `CostLimitExceeded`; `Evaluate` is `Run(CreateFrame(…))` and nothing else. The internal `Frame.ChargedUnits` is the limit minus the remaining units, 0 without a meter.

## Cost

- Without a limit there is no meter: nothing is counted, no formula is computed, no `CelCostFunction` is called, and a node tests one field of the frame.
- `Charge(units)` subtracts from the remaining units. More units than remain — a sum that does not fit the counter included — means the operation does not run: the meter throws `CostLimitException`, and `Plan.Evaluate` returns `CostLimitExceeded` at the recorded node as the single error. A total equal to the limit is allowed. The exception is not an error value, so `||` and `all` cannot absorb it.
- An argument that is invalid without work on the data — a list index out of range — fails after the constant unit only, before the formula of the operation.
- The frame, with its slots and argument stack, is allocated once before the root is evaluated and is not charged; everything allocated after it counts against the bound of B = 64 bytes per unit that the property test of cost checks.
- What the bound asks of the values of this part. A list of n elements holds n values of 32 bytes and costs 1 + n. A map of n entries holds 2n values, a key and a value each, so it costs 1 + 2n and takes at most 64 · (1 + 2n) bytes with its index, at every n ([values](values.md), "Lists and maps"). An error value takes at most 64 bytes ("Errors as values"), so an operation of 1 unit that fails, such as `1 / 0`, fits.

**Application data** — the rows of the cost table for application data, charged by the node or the implementation that does the work, before it:

| Operation | Units | Where |
| :- | :- | :- |
| `e.f` and `has(e.f)` on an object | 1, whatever the field holds; the pair of the place rule and the adapter of a JSON value read are inside it | `FieldPlanNode`, `SelectPlanNode` |
| enumeration of a map view ordered by ascending key, n entries | 1 + c · n · ⌈log₂(n + 1)⌉ before the first entry, at each enumeration, also when the view keeps its sorted keys; c is 1 for integer, `bool` and enumeration keys, 1 + ⌈2 · Lmax/10⌉ for `string` and `Guid` keys (`Guid`: Lmax = 36) | the operation that enumerates: a comprehension over the map, `cel.@mapInsert` with a map, equality, the check against a declared type; the result conversion, which is not charged, enumerates without it |
| key lookup of length L in a JSON object of n properties: index, selection, `has` | 1 + n · (1 + ⌈L/10⌉), instead of the map rows | `SelectPlanNode`, `index_map` |
| `size`, enumeration of a JSON object | 1 + Σ (1 + ⌈Lᵢ/10⌉), Lᵢ the length of the raw UTF-8 name, the term of a property before it; instead of `size_map` and `map_size` | the size functions, the comprehension, `cel.@mapInsert` with a map, equality |
| `in` on a JSON object, key of length L | the row above + ⌈L/10⌉; instead of `in_map` | `in_map` |
| equality of JSON objects | the row of two maps, the lookup in the second by the JSON lookup row, after the check for repeats of both | `EqualityRules` |
| index of a JSON array of n elements | 1 + n, instead of the unit of `index_list` | `index_list` |
| a set of n elements that an application function returns, read as a list | 1 + c · n · ⌈log₂(n + 1)⌉, c as above for `string` and `bytes`, 1 otherwise ("Application functions") | the call, after the implementation, before the sort |
| a collection without an index of n elements that an application function returns | 1 + n | the call, after the implementation, before the copy |
| a JSON string value of length L read | 1 + ⌈L/10⌉ at each read, before the string is created; L is the length of the raw UTF-8 token without its quotes, escape sequences included, the upper bound that is known without decoding, as Lᵢ of a name; it is the decoded length for a string without escapes and without non-ASCII characters. The property names of an enumeration are inside the terms of their row and are not charged again | the node that reads it: the selection, the index of an array, the element of a range or of a comparison, and the identifier of a variable bound to a JSON string |
| equality of two objects | 1 + Σ over the fields compared: 1 for each of the two reads + eq of the values | `EqualityRules` |
| check against a declared type | n before descending into a list of n elements or a map of n entries; a typed view that already fits, 0 | as for the bindings of this part |

The memory of each row stays within B per unit: a pair or a JSON adapter is one object of at most 64 bytes inside the unit of its read, and the sorted keys of a map view, n references, are inside the n · ⌈log₂(n + 1)⌉ units of the sort. The rows of sets and of collections without an index read as members, of struct members, and of the unpacking of `google.protobuf.Any` come with the generator and protobuf; a set and a collection without an index bound as a variable are converted by `CelBindings.Add`, before the evaluation, and cost nothing; returned by an application function they are copied at the call by the two rows above.

## Extension sets in the evaluator

The calls of the functions of the sets are calls like the others: the candidates that type checking recorded, a `CallPlanNode` or a `DispatchPlanNode`, the marks of step 3 of "Calls". Four things are new.

- **`ShallowArguments`.** An `OverloadBinding` with this flag has no argument marked for the check at depth, whatever its static type; `Matches` checks the top level of each argument, and the implementation reads the elements itself ([extension-library](extension-library.md)). The flag is for the list forms of `math.@max` and `math.@min` and for the two `flatten` overloads.
- **Evaluation without type checking** finds the functions of the sets as it finds any other: a receiver call whose target is a chain of names — `math.ceil(x)`, `base64.encode(b)`, `ip.isCanonical(s)` — is first looked up as a qualified function name among the function names of the index, and when it is there it is a global call with the arguments alone, as in [checking](checking.md#name-resolution); otherwise the call is a `DispatchPlanNode` over all overloads of its name, call style and argument count, those of the sets included. A call with a qualified name that no set declares is `EvalNoMatchingOverload`.
- **Special forms.** `cel.@block`, like `conditional`, has no implementation; the planner evaluates it ([Blocks](#blocks)). The calls of `cel.@mapInsert` that sit in the step of a macro become `MapInsertPlanNode` ([Comprehensions of two variables](#comprehensions-of-two-variables)).
- **Implementations of the sets** use `CallSite.Charge` and the pooled `ResultBuilder` to charge as a result grows ([extension-strings](extension-strings.md#conventions)); they throw nothing and keep no state, so they serve any number of threads like the standard library.

## Comprehensions of two variables

A `ComprehensionNode` with `IterVar2` is planned with three slots: the first iteration variable, the second and the accumulator. `ComprehensionPlanNode` evaluates the range as for one variable — an error value is the result, another value than a list or a map is `EvalInvalidComprehensionRange` — and then, for each element in order:

| Range | First variable | Second variable |
| :- | :- | :- |
| list | the index, an `int` from 0 | the element |
| map | the key | the value, taken from the same enumeration that gives the key, in the order of the map, with no lookup by key |

The rest — the loop condition, the event for cancellation, 1 unit for each executed step, the step into the accumulator, the result after the loop, no early exit on an error value — is as for one variable. The enumeration rows of the cost table for a map view and for a JSON object ([evaluation cost](#cost), application data) already charge for the entry, so the read of the value is part of them; an adapter that cannot give a pair without a lookup charges the row of the lookup.

The hidden accumulators `@result` and `@__sortBy_input__` are recognized as those of the standard macros are, and so is the first iteration variable that `transformMap` puts into `cel.@mapInsert(@result, i, t)`: the reads that the expansion adds cost nothing and are part of the step. Reads of a name that an author wrote — the variable of `cel.bind`, the iteration variables — cost 1 as any identifier read does.

**`transformList`.** Its step, `@result + [t]`, or `p ? @result + [t] : @result` with a filter, becomes an `AppendPlanNode` as the step of `map` does: the accumulator holds a list builder, 1 unit is charged for each element added, and the empty list of the initializer is 1 unit.

**`cel.@mapInsert` and the maps.** The step of `transformMap` and `transformMapEntry`, `cel.@mapInsert(@result, …)` or `p ? cel.@mapInsert(@result, …) : @result`, becomes a `MapInsertPlanNode` in a comprehension whose accumulator is the hidden `@result` and whose initializer is `{}`: the accumulator slot holds a `MapBuilder`, an array of entries that grows by doubling from 4 entries, and the node inserts into it; the read of `@result` in the result turns the builder into the map of [values](values.md) with its index, made once. The node evaluates the accumulator, then the key, then the value (the second overload: the accumulator, then the map); it is strict: an error value among them becomes the accumulator, and an accumulator that is an error value stays. Each insertion, in this order: the key must be an `int`, `uint`, `bool` or `string`, otherwise `UnsupportedMapKeyType` (3027); the charge, 2 units and ⌈L/10⌉ more for a string key of length L, before the pair is put in; a key equal by CEL equality to one present is `DuplicateMapKey` (3010) at the call of `cel.@mapInsert`, with the later key written as `DuplicateMapKey` writes it. `UnsupportedMapKeyType` is placed at the same call: the key is an index or a key of a map, so a key of another kind comes only from a tree that no text writes, and the call is its only place. The second overload inserts the entries of its argument in the order of that map, each with the same checks and charges, so a map of m pairs costs 2m and the keys. The argument is enumerated as the range of a comprehension is: a map with an error among its keys, or a JSON object with a repeated name, is that error at the call before the first pair; the enumeration row of the cost table for a map view ordered by ascending key or for a JSON object is charged before the first pair, in addition to the pairs; the order is that of the enumeration — the properties of a JSON object in their order, a sorted view by ascending key. An entry whose value is an error value makes the result of the step that error value, placed at the call. The initializer `{}` is 1 unit, the cost of a map literal of no entries.

The generic implementations of `@mapInsert_map_key_value` and `@mapInsert_map_map` serve a call that is not in such a step. Text cannot write the name, so only a tree that `NodeFactory` built reaches them; they copy the first map, add the pairs with the same checks, and charge the row of the table alone. The copy of the first map is not charged: only a tree made inside the library reaches these implementations, as in its tests, and no public API builds a tree, so the cost bounds every expression that a text or an application gives. A public source of trees would charge the copy as a map literal of the entries copied.

## Blocks

`cel.@block(slots, result)` is planned from its two arguments when the first is a list literal without optional elements, which type checking has checked ([checking](checking.md#calls-that-the-checker-validates)). In evaluation without type checking a first argument that is not such a literal makes the call a node that returns `EvalNoMatchingOverload` at the call after its arguments are evaluated, as for any call with no overload that fits. A block of no slots is planned as its result.

A block of n slots has n plan nodes, one for each element of the literal, and the node of the result. The planner gives it n value cells and n state cells in the frame, assigned like the slots of variables and of comprehensions: they live in the arrays that `CreateFrame` allocates once, are not charged, and are bounded by the size of the text. The list of the slots is never created.

- **Slot references.** An identifier `@index` followed by the digits of N, without a sign or a leading zero, with N below the slot count of the innermost enclosing block that has that many slots, is a `SlotPlanNode` of that cell: an inner block shadows the outer one for the numbers it has, and the rest go to the outer block. The slot expressions and the result are inside the scope. Any other name that starts with `@index` is an identifier like the others — a variable of an internal set, or unbound.
- **Evaluation.** Entering the block takes a new epoch from the frame, a counter that grows by one at each entry, so a block in the body of a comprehension starts fresh at each iteration without clearing its cells. A slot is read once per epoch: the first read marks the cell as in progress with the epoch, evaluates the slot node, stores the value — an error value too — and every later read of that epoch takes the stored value. A slot that nothing reads is never evaluated and its error never happens. A slot that reads itself, directly or through other slots, finds its cell in progress and is `Unbound` (3009) for its own name: `no value is bound to variable '@index0'`.
- **Cost.** The block node charges nothing. A slot costs what its expression costs, once, at the first read; each read of a slot is 1 unit, a read of a variable. The result costs its own expression.
- **Tests.** The tests build the tree with `NodeFactory` and plan it with `Planner.PlanWithoutTypeCheck`, then call `Plan.Evaluate` with a cost limit where they need one: the set has no macro to write it with. They check that a slot is evaluated once however often it is read, with an application function that counts its calls; that a slot nobody reads is not evaluated and its error does not appear; that a slot may refer to a later one and to itself (the second is `Unbound`); that an inner block shadows an outer one; that a block in the body of `map` is fresh at each element; that an empty block is its result; that the cost is the slots read plus the reads; and that a first argument that is not a literal gives `EvalNoMatchingOverload` there and, through the internal `Check`, `NoMatchingOverload` on a checked tree.

## Time

Time adds no node and no frame state. The database of the environment reaches the functions of time through the call site.

**Receivers and zones.** A receiver of `timestamp` or `duration`, with a zone or without, is a call like any other: a `CallPlanNode` when type checking leaves one candidate, a `DispatchPlanNode` for a `dyn` receiver or argument or without type checking. Candidates are chosen by the kinds of the values: `dyn(duration('1s')).getHours()` takes `duration_to_hours`; with a zone argument no candidate takes a duration, and the call is `EvalNoMatchingOverload` at the call. The environment gives its `CelTimeZoneDatabase` to the planner, `Plan` keeps it and `Frame` hands it to `CallSite.TimeZones`; it is `null` when `UseTimeZones` was never called ([time zones](time-zones.md)). The name of the zone is resolved inside the implementation at each call, by the order of "Resolving a zone name" there, so a constant zone and a zone read from a variable or from `dyn` take the same path.

The planner does not look up a constant zone. The reasons: a wrong constant must fail when the call is evaluated, at the call, and only then — a branch of `?:` that is not taken, the right side of `||` after `true` and the right side of `&&` after `false` have no error — which per-call resolution gives with no extra rule; the lookup is a binary search over a sorted array of strings and allocates nothing, so there is nothing to save; and one path cannot differ from another in a value or a cost. The call evaluates its arguments from left to right: an error value of the receiver is the value of the call, then one of the zone, and only then do the kinds of the arguments and the name of the zone matter. `TimeZoneNotFound` (3022) and `InvalidTimeZone` (3023) are errors of the call, found after the kinds are checked, so `timestamp(0).getHours(5)` is `EvalNoMatchingOverload` and `timestamp(0).getHours('Mars')` is 3022.

**Constants of time.** For a `CallPlanNode` whose overload is `string_to_timestamp` or `string_to_duration` and whose argument is a string literal, the planner runs the implementation once at planning, on a call site with no limit, no database and the offset of the call. A value becomes a `ConstantPlanNode` with the value and the units of the call it replaces — `FixedCost` plus the argument cost of the literal, 1 + ⌈L/10⌉ — charged when the node is evaluated, at the position of the call. An error value is not folded: the call stays, and the error comes when it is evaluated, at the call. So `timestamp('x')` compiles, `false && timestamp('x') == timestamp(0)` is `false`, and `timestamp('x').getHours()` is `InvalidArgument` at the `(` of `timestamp`. Folding is an optimization and changes no value, error or cost: evaluation without type checking, whose calls are `DispatchPlanNode`s, folds nothing and gives the same value and the same units as the checked plan. A folded constant allocates nothing when it is evaluated.

**Evaluation without type checking.** The same functions, the same rules, no extra case. A time value of a binding is converted by the static type of `T` at `CelBindings.Add`, whether or not the variable is declared, so a `DateTimeOffset` is a `timestamp` there too; no declared type is consulted, and a variable declared `timestamp` that holds a string is not an error without the check ([values](values.md), "Fits a type"). Every argument is marked, a time scalar fits its kind and nothing else, and a call that no overload takes is `EvalNoMatchingOverload`: `timestamp(0) + 1`, `timestamp(0).getHours(5)` and `duration('1s').getHours('UTC')` are that error at the call. `timestamp('x')` is `InvalidArgument`; the zone errors and `Overflow` are those of the checked path. The rows `WithoutTypeCheck` of the examples and the property of checked against unchecked evaluation, with time in its generator ([tests](tests.md)), hold the two paths together.

**Cost of time**, every row charged by the call before it runs, as the standard library rows of [library](library.md):

| Operation | Units | Where |
| :- | :- | :- |
| `timestamp(string)`, `duration(string)`, folded or not | 1 + ⌈L/10⌉, L the UTF-16 length of the string | the call; the folded node |
| `timestamp(int)`, `int(timestamp)`, `int(duration)`, `timestamp(timestamp)`, `duration(duration)` | 1 | the call |
| `string(timestamp)` | 1 + ⌈Lᵣ/10⌉ with Lᵣ = 20, or 21 plus the digits of the fraction, from the nanoseconds | the call, before the string is made |
| `string(duration)` | 1 + ⌈Lᵣ/10⌉ with Lᵣ at most 22, from the value | the call, before the string is made |
| a receiver without a zone; `+`, `-` and the relations of time | 1 | the call |
| `==` and `!=` of two time values | 1 as eq of two scalars, at any depth in a list or a map | `EqualityRules` |
| a receiver with a zone, constant or not | 1 + ⌈L/10⌉, L the UTF-16 length of the zone string; the lookup is inside it | the call |
| the read of a variable of time; the check of its binding at the first read | 1; the check is the top level only, 0 | `VariablePlanNode` |
| a time field of an object | 1, as any field | `FieldPlanNode` |
| a time argument or result of an application function | the check of the type charges 0 for a scalar; no copy | the call |
| a call that fails | its units as above; the error value holds references and numbers only — the zone string, the database, the text of the string, a number in a field — at most 64 bytes | the call |

The rows that a measurement of the earlier parts found missing came from operations whose work grows with data that no argument length shows. Time has three that could: the length of the zone string of a receiver (the receiver is not a string, so the argument cost reads the other argument), the length of the result of `string()` (known before the string exists), and the folded constant (the same units as the call). A time scalar has no data to copy and no elements to check. The test of memory against units ([tests](tests.md), "Properties of evaluation") gets time in its generator and in its rows: the 1-unit failures `timestamp(253402300800)` and `timestamp(0).getHours('+1:5')` fit B per unit without the error allowance E; E = 256 is added to a case of the generator that ends in an error exactly as for the other kinds; and the rows `string(timestamp)` and `string(duration)` hold their string of at most 30 characters inside B per unit.

## Message literals

`T{f: v, …}` of a constructible description is planned as a `MessagePlanNode` with the description, the value nodes in the order of the text and, for each entry, the number of its field. With type checking the planner takes both from the reference map ([checking](checking.md#message-literals-of-constructible-types)); without it, by the rule at the end of this section.

**Evaluation**, in this order:

1. The values are evaluated from left to right, as the values of a map literal are, and an error value is the result at once, the later values not evaluated.
2. The node charges, once, `1 + n + ⌈L/10⌉`: n is the number of entries as written, a repeated name counted each time; L is the sum of the lengths of the values that are strings, in UTF-16 units, and bytes, in bytes — only the values written directly in a field, not the elements of a list or a map. This is the class of the creation of an object of the cost table, with the length of what a literal writes: `bytes` are copied into the message, and the content of an `Any` is parsed from them. The units are charged after the children and before the creation; without a cost limit L is not computed.
3. Each field number that occurs more than once keeps the last value; the earlier values were evaluated and charged. The numbers are then distinct and in the order of their last occurrence, as `CreateInstance` requires ([objects](objects.md#members-for-protobuf-messages)).
4. The node counts one event, since it calls code of the application, and calls `CreateInstance(fieldNumbers, fieldValues)` inside the exception boundary of "Application functions": an exception other than the ones that pass is `ApplicationException` with the callee `the creation of an object of type '{type}'`. The value it returns is the value of the literal: an object, a converted value of a known type, or an error value without a position, which gets the position of the literal, the `{` of the message name.
5. The instance is not changed after it is created, so a shared value is safe: a message put into a field of another literal is that instance.

**What the literal is.** The value of a literal of an ordinary message is the object the description made. The value of a literal of a known type is what the type converts to — `Int32Value{value: 1}` is `1`, `Value{bool_value: true}` is `true`, `Struct{…}` a map — which the package returns from `CreateInstance` ([protobuf-messages](protobuf-messages.md#literals-of-the-known-types)); the node does not look at the value.

**Cost, the row of the table.** The row of the class of creation for a message, which was `1 + n`, reads `1 + n + ⌈L/10⌉` as above; the cost of a literal of the known type `Any` includes the unpack of its content, the amount that a read of an `Any` field charges.

**Evaluation without type checking.** The planner has no reference map, so the name of the type resolves at evaluation as the identifiers do: by the candidates of the container, the first that is an object type description of the type index wins, and a variable of that name does not count. No candidate, or a description that is not constructible, is `Unbound` for the name as written. A field name that the description does not have is `EvalNoSuchField` (`no such field '{field}' in {type}`) at the literal; a value that does not fit its field is the error of `CreateInstance` ([protobuf-messages](protobuf-messages.md#literals)). Literals of known types and the rest are as with the check.

## Charges of a described object

A description may add to the charges of an object, with the two virtual members of [objects](objects.md#members-for-protobuf-messages), and only when the evaluation has a cost limit:

- **Reading a field.** `FieldPlanNode` and `SelectPlanNode` on an object value charge the unit of the selection, then `FieldReadCost(instance, number)`, then count the event and call `GetField`. `has(e.f)` calls neither. A description that does not override the member adds 0.
- **Equality.** `ObjectRules.AreEqual`, which the equality of two objects, of two lists or maps that hold objects, `in`, and `CelValue.CelEquals` of two values with a description share, asks the description for `EqualityCost(left, right)`: `null` is the default rule of [objects](objects.md#equality-of-objects) with its pair-by-pair charges; a number is charged once, and then `CelEquals(left, right)` decides inside the exception boundary. The row of two objects in the cost table is that rule for the descriptions of the generator and of types described at run time; for a protobuf message the row is the one the package gives ([protobuf-messages](protobuf-messages.md#equality)).

## Cancellation

When the token can be canceled, the frame counts events: the steps of comprehensions, the calls of application functions and the field reads and presence tests of objects. Before each event, `Event()` checks the token when the count is a multiple of 64 — so before the first event and then every 64 — and increments the count; a canceled token throws `OperationCanceledException` out of the evaluation. After the signal at most 64 events begin. With `CancellationToken.None` nothing is counted.

## Errors as values

An error inside evaluation is a value of the kind `Error` of the stage `Evaluate`; nodes return it like any value. Its position is the offset of the node that failed. The value keeps the code, the offset and the parts of the message by reference; the text and the line and column are formed only when a `CelError` is read, after the evaluation or through `CelValue.TryGetError`, so an error that `||` absorbs costs no text. Creating an error value allocates at most 64 bytes: one object, with no string, no boxed number and no array. The parts of its message are references to objects that already exist — a name of the text, a string argument, a list, a type, an overload, a node of the plan, a type that a check charged for found — or a number in a field of the object. The one allowance is the kinds of the arguments of `EvalNoMatchingOverload` for a call of more than 16 arguments, which only an application function can have: they take an array of one byte per argument, bounded by the text of the program; and the names of the object and abstract arguments of a call whose static type was `dyn`, one array of references bounded by the number of arguments; among more than 16 arguments an abstract argument is named `abstract`. ## Evaluation without type checking

`Planner.PlanWithoutTypeCheck(ParsedExpression, DeclarationIndex, CelTimeZoneDatabase?)` serves the internal entry point `CelEnvironment.EvaluateWithoutTypeCheck` (see [facade](facade.md)). It plans the parsed tree with the same nodes and no checked expression:

- names resolve at evaluation as [checking](checking.md) resolves them at compilation, with "has a value in the bindings" in place of "is declared": comprehension variables first, then the qualified names of an identifier or a selection chain, the longest first, each by the candidates of the container; for each candidate a value in the bindings, else a type identifier of the version. No candidate is `Unbound` for the name as written. Values are not checked against declared types;
- a selection on a value is a `SelectPlanNode`, which finds a field of an object by name; variables of an object type apply the place rule at the first read; a message literal is planned as "Message literals" says;
- comprehensions and the special calls are planned as with type checking; any other call becomes a `DispatchPlanNode` over all overloads of its name, call style and argument count in the declaration index, the overloads only with `dyn` included; without static types every argument is marked. A function without such overloads is `EvalNoMatchingOverload` once the arguments are evaluated without error;
- no argument is prepared: there is no checked expression whose references could hold a prepared object, and nothing here calls the preparers of [declarations](declarations.md). `matches('abc', '(')` is `EvalInvalidRegex` at the call, the literal pattern handled as a pattern from data; `matches(1, 'a')` is `EvalNoMatchingOverload` (`no such overload: matches(int, string)`) and so are `matches('abc', 1)`, `matches('abc')` and `'abc'.matches(1)`, from the dispatch over `matches` and `matches_string` by call style and argument count.

So `f_unknown(17)` evaluates to `EvalNoMatchingOverload`, and `x` without a binding to `Unbound`. The value of the root is returned as it is, without conversion to a .NET type.
