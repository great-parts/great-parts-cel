# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).
From 1.0.0 the public API follows Semantic Versioning; see [Versioning and compatibility](docs/versioning.md).

A change of the result or of the error of an expression that was valid in an earlier version is listed under `Behavior changes` of its version.

A fix of a vulnerability is listed under `Security` of its version, with the GHSA identifier of its advisory and the CVE identifier when one is assigned; see [SECURITY.md](SECURITY.md#where-a-fixed-vulnerability-is-announced).

### Added

- The package `Great.Parts.Cel.DependencyInjection`: `AddCel` and `AddKeyedCel` register a CEL environment, its compilation cache and an `ICelEvaluator` as singletons, one for the application or several by name (keyed services); `CelOptions` sets the default cost limit and the capacities of the cache, bound by the application itself; `ValidateCel` validates the options of an application with a CEL expression over their fields. The package reads no configuration and uses no reflection, so it works under Native AOT.
- The package `Great.Parts.Cel.AspNetCore`: `RequireCel` and `RequireCel<TResource>` add CEL expressions over the claims of the user and the resource to authorization policies as a `CelAuthorizationRequirement`, with `AddCelAuthorization`; `WithCelValidation<TRequest>` validates the request of a minimal API endpoint or of every endpoint of a group, and answers 400 with a validation problem; `CelValidateAttribute<TRequest>` does the same for an action of an MVC controller. The endpoint filter works with the request delegate generator under Native AOT.

An unknown operand lets the rest of the expression finish, an error of a strict call is the result before an unknown operand, as the language definition says, and an unknown attribute costs 1 unit.
- Asynchronous functions: `AddAsyncFunction` (up to four parameters) and `AddAsyncMethod` (a receiver and up to three parameters) declare a function whose implementation returns a `ValueTask` and takes the `CancellationToken` of the evaluation after its parameters, and `AddAsyncFunctionImplementation` binds a `CelAsyncFunctionImplementation` to a declared overload. `EvaluateAsync` and `EvaluateInputAsync` of `CelProgram<T>`, `CelEnvironment`, `CelCompilationCache` and `ICelEvaluator`, and `EvaluatePartialAsync`, evaluate an expression that calls them. The library evaluates the expression in passes, starts the calls that a pass finds in one wave, at most `CelEvalOptions.MaxConcurrentAsyncCalls` at a time (`DefaultMaxConcurrentAsyncCalls`, 100), runs each distinct call once and awaits the calls without blocking a thread; it creates no threads, tasks or timers. The cost limit applies to the sum of the passes and of the calls, added in the order in which the calls started, so the result does not depend on timing, and a program with no call that waits completes in its first pass, synchronously. `CelProgram<T>.HasAsyncCalls` tells whether a program can call such a function. `Evaluate`, `EvaluateInput` and the synchronous one-step calls of such a program evaluate nothing and return the error `AsyncEvaluationRequired` (3029), which names the function; `EvaluatePartial` describes such a call as an unknown part. In `Great.Parts.Cel.AspNetCore` the authorization handler and the filters evaluate asynchronously and pass the token of the request, so a request that was aborted stops the calls that wait. See [Application functions](docs/recipes/application-functions.md#asynchronous-functions).
- The package `Great.Parts.Cel.Filtering`: `CelFilterCompiler` translates a filter of [AIP-160](https://google.aip.dev/160) into a CEL expression of an environment, type-checks it and returns a `CelProgram<bool>` or all errors (`Compile`), or returns the expression with the positions of its nodes in the filter, for an application that translates further (`Parse`); `CelFilterOptions` names the search fields and the enumeration types of integer fields. The fields of a filter are the variables of the environment and the fields of their types, the filter comes from a client, so every problem is an error at its place in the text and the length, the depth and the number of errors are limited, and the package works under Native AOT and on `browser-wasm`. The error codes `FilterSyntaxError` (1012), `InvalidFilterValue` (2015) and `InvalidFilterRestriction` (2016). The core has the members that the package needs and any other translator can use: `CelExprFactory.CreateError`, `CelParseResult.FromParsedExpr`, `CelParseResult.FromErrors`, `CelCompileResult<T>.FromErrors`, `CelDuration.TryParse` and `CelTimestamp.TryParse`. AIP-160 has no test suite, so the package is checked by a corpus of its own; see [Conformance](docs/conformance.md#aip-160-filters).
- The package `Great.Parts.Cel.Policy`: `CelPolicy.Parse` reads a CEL Policy document in YAML, as the `policy` package of cel-go does, with all errors at their place in the document (`InvalidYaml` 1010, `InvalidPolicy` 1011), and `Compile<T>` composes its rules, matches and variables into one program of an environment, with `WithExplanationOutputs` for the explanation of a match; the checks of the composition are the errors `IncompatibleOutputTypes` (2012), `UnreachableMatch` (2013) and `OverlappingVariable` (2014). The document may come from a client, so the reader and the composition are limited (the depth of the rules, the number of rules, matches and variables, the budget of text) and never recurse by the depth of the document. The core has the points the package needs: `CelSourceSegment` and `CelCompileOptions.SourceSegments`, `CelError.Create`, the public constructor of `CelException`, `CelEnvironmentBuilder.AddAbbreviation` with the error `InvalidAbbreviation` (4020), and the types of the slots of `cel.@block`. The package is checked by the policy suite of cel-go.
- Documentation and samples for a first use: the page [Getting started](docs/getting-started.md) with seven scenarios, from the simple entry to a web service with a cache and bulk evaluation; the columns `Common cause` and `Fix` of the table of [Error codes](docs/error-codes.md), a cause and a fix for every code, as the troubleshooting guide; the recipe [FluentValidation](docs/recipes/fluentvalidation.md); the runnable samples in `samples/` (`SimpleEntry`, `EnvironmentAndJson`, `AppObject`, `ValidateOnSave`, `AppFunctions`, `WebService`, `CacheAndBulk` and `FluentValidation`); and a README and an `AGENTS.md` in each of the six packages (`Great.Parts.Cel`, `Great.Parts.Cel.Protobuf`, `Great.Parts.Cel.DependencyInjection`, `Great.Parts.Cel.AspNetCore`, `Great.Parts.Cel.Policy` and `Great.Parts.Cel.Filtering`), shown on nuget.org.

### Changed

- Reading `CelEvalResult<T>.Value`, `CelBuildResult.Environment` or `CelCompileResult<T>.Program` of an unsuccessful result throws `CelException` with all errors, where it threw `InvalidOperationException`.
- `default(CelEvalResult<T>)`, a structure that no call returned, is not successful and has no errors; reading its `Value`, `GetValueOrThrow()` or `Cost` throws `InvalidOperationException`. `CelObjectType.CreateInstance` throws `InvalidOperationException` by default, where it threw `NotSupportedException`.
- Evaluation is faster and allocates less, with the same results, errors and costs: a thread keeps the frame of its evaluations for the next one, so a thread that evaluates again and again allocates no frame; a list literal of constants, such as `['RUB', 'USD', 'EUR']`, is one constant of the plan and no evaluation builds it; the read of a field and its comparison with a constant, such as `order.total > 1000.0`, are one node of the plan that gives the same value or the same error at the same place and charges the same units in the same order. Where the results or the costs of the searches below differ, it is under `Behavior changes`.
- `contains`, `indexOf`, `lastIndexOf`, `replace` and `split` search a pattern that is a literal of the expression with a `SearchValues<string>` that compilation prepares, and any other pattern with the ordinal search of .NET; the search of the library for a longer pattern, which took time linear in the lengths, is gone, and the cost of a pattern longer than 64 UTF-16 code units grows with its length (see `Behavior changes`). The search for the literal prefix of a pattern of `matches` is not changed and stays linear.
- The simple entry takes less time and allocates less, with the same results, errors and costs: the registry of anonymous types is read in constant time and without a lock; a call finds the environment of an anonymous type through a reference that its entry of the registry keeps, and a program through the string instance of its text, without hashing the text (a text that is equal in value in another instance is found by its value); the bindings of a call are one set for each thread, cleared when the call ends, so a call keeps no reference to the data of the application after it returns.
- `CelMap.Create` has a second overload, `CelMap.Create(params ReadOnlySpan<KeyValuePair<CelValue, CelValue>>)`, beside the one with `IEnumerable` (source-breaking): a collection expression, `CelMap.Create([...])`, binds to it and makes no collection of its own for the entries; the map and the checks are the same. A call `CelMap.Create(null)` does not name one overload any more, since `null` fits both: cast it to `IEnumerable<KeyValuePair<CelValue, CelValue>>` to get the `ArgumentNullException` as before.
- On `net11.0` the packages are compiled with runtime async, which Microsoft calls a preview feature of .NET 11: the `async` methods of the library, those that evaluate asynchronous functions, are methods of the runtime and not state machines of the compiler, and Native AOT supports it. An application turns nothing on and the public API is the same. WebAssembly applications run on a runtime that does not run such methods, so the package `Great.Parts.Cel` also carries the same assembly built without runtime async, in `runtimes/browser-wasm/lib/net11.0/` and `runtimes/wasi-wasm/lib/net11.0/`, which NuGet gives to an application with that runtime identifier. The `net10.0` build is not changed. If a problem is found in the feature, a fix release takes it out and changes no API.
- `matches` with a pattern that is a string literal runs a deterministic automaton that the compilation builds, with the same results, errors and costs: one table lookup for each code point, and between the places where a match can begin a jump to the next occurrence of the literal prefix of the pattern (`'ORD-[0-9]+'`) or to the next of the characters that can start a match, when they are a few or all ASCII (`'[0-9]{4}-[0-9]{2}'`). A pattern with `(?m)`, `\b` or `\B`, a pattern from data, and a pattern whose automaton would pass 256 states, 64 classes of characters or 200,000 steps of work are run by the engine of sets of states as before, which now also jumps to the next occurrence of the literal prefix and stops after the start of the text for a pattern that begins with `^` or `\A`. An entry of the cache of patterns weighs the size of the program plus its tables in units of 16 bytes; the capacity, 100,000, does not change.
- On `net11.0` (source-breaking) the members of `Decimal128` have new names, since `FromDecimal(decimal)` and `TryGetDecimal(out decimal)` take the old ones on both targets: `CelValue.FromDecimal(Decimal128)` is `CelValue.FromDecimal128`, `CelValue.TryGetDecimal(out Decimal128)` is `CelValue.TryGetDecimal128`, and `CelObjectType.FromDecimal(int, Decimal128)` is `CelObjectType.FromDecimal128`.
- `distinct` and the functions of the extension set `sets` look an element up by a hash that agrees with CEL equality instead of comparing every pair, so the time of a call grows with the length of the list and not with its square. The results, the errors and the order in which the code of the application is called are as before; the cost is the one under `Behavior changes`.
- `GPCEL007` is not reported any more (a removed diagnostic): a `System.Decimal` member is a field of the type `decimal` on both targets.
- The message of `TypeNotConstructible` no longer says that only protobuf messages can be created by an object literal; the code and the place are as before.

### Behavior changes

- On `net11.0`, with no compile error: code of 1.x that calls `TryGetDecimal(out var value)` still compiles, and `value` is now a `decimal`; the method returns `false` for a value that `System.Decimal` does not hold exactly (more than 96 bits, an exponent below -28 or a value beyond its range). Read such a value with `TryGetDecimal128`.
- The range of `duration` is that of `google.protobuf.Duration`, from `-315576000000.999999999s` to `315576000000.999999999s` (about ±10 000 years), as the language definition says; it was a 64-bit number of nanoseconds, about ±292 years. A longer duration is now a value where it was `Overflow` (a sum or a difference of durations, the difference of two timestamps) or `ConversionRange` (`duration(string)`, a `TimeSpan` of the application, a `google.protobuf.Duration` field of a message). `duration('9223372036854775808ns')` is `9223372036.854775808s`, and `duration('9223372036854775808ns9223372036854775808ns')` is `18446744073.709551616s` where it was `0s`. `int(duration)` is `ConversionRange` when the nanoseconds do not fit an `int`.
- `CelDuration.TotalNanoseconds` throws `InvalidOperationException` for a duration whose nanoseconds do not fit a `long`; read `Seconds` and `Nanoseconds` instead.
- A variable of the application named `decimal` is the build error `DuplicateType` when the `decimal` extension set is added, since the name of a type and of a variable must differ; rename the variable. Without the set the name is free as before.
- The cost of `contains` and of the functions `indexOf`, `lastIndexOf`, `replace` and `split` of the extension set `strings` multiplies the part of the lengths, ⌈Lₐ/10⌉, by q = max(1, ⌈Lₚ/64⌉), Lₚ the length of the string searched for in UTF-16 code units: a pattern of at most 64 code units costs what it cost in 1.x, a longer one costs q times as much for the part of the lengths. The search is not linear in the worst case, so the cost pays for the worst case: a pattern that is a literal is searched by a `SearchValues<string>` that compilation prepared, any other pattern by the ordinal search of .NET. A limit that a call passed in 1.x it may not pass in 2.0 when the pattern is longer than 64 code units. `contains` now also rejects, as the other functions do, a match that would cut a surrogate pair, which only a pattern with a lone surrogate from the data can make. See [Cost](docs/cost.md#the-search-for-a-substring).
- The cost of `distinct`, `sets.contains`, `sets.intersects` and `sets.equivalent` is the hashing of the elements and the one comparison of each element that is found, where it was the comparison of every pair: `[1, 2, 3].distinct()` costs the same, `[1, 2, 2].distinct()` costs 1 more, and a call on long lists costs much less; an element that holds an object of the application is still compared with the others of its kind in the order of the pairs. A limit that a call passed in 1.x it may not pass in 2.0 when a list is short, since the hashing of each element is charged. A number of 2^53 or more in absolute value (an `int`, a `uint` or a `double`, an infinity included) is not hashed, since CEL equality is not transitive from there on: such numbers, and values with an error inside, are compared with each other in the order of the pairs, so a long list of identifiers of 64 bits costs and takes as in 1.x, and a value with an error inside is no longer compared with a value of another kind. The `sets` functions index the whole list that is looked in, so an element of it that is an error ends the call wherever it stands. See [Cost](docs/cost.md#hashing-in-distinct-and-sets).

## [1.0.0] - 2026-11-17

The first stable release of the packages `Great.Parts.Cel` and `Great.Parts.Cel.Protobuf`, for `net10.0` and `net11.0`, under JIT and under Native AOT.

### Added

- Compilation and evaluation of CEL expressions. `CelEnvironmentBuilder` collects declarations and builds an immutable `CelEnvironment`; `CelEnvironment.Compile<T>` parses, type-checks and plans an expression into a `CelProgram<T>`, which is evaluated any number of times, from any number of threads, with `CelBindings` and `CelEvalOptions`, and gives its result as the requested .NET type. `CelEnvironment.Evaluate<T>` does both steps in one call, and `CelCompilationCache` keeps the compilations of one environment. An error of any stage is returned as a result with a code of `CelErrorCode`, its stage and its place in the expression. See [API concepts](docs/api-concepts.md) and [Error codes](docs/error-codes.md).
- The complete CEL syntax, type checking by the gradual type checking of the CEL language definition, and the standard library, version 1 (`CelStandardLibrary.V1`): logic, equality, arithmetic and ordering, also across `int`, `uint` and `double`, conversions, strings, lists and maps, `timestamp` and `duration` with their receivers and time zones, the standard macros, and `matches` with the syntax and the semantics of RE2, found in time linear in the length of the string. See [Standard library](docs/standard-library.md).
- Extension sets, each added with an explicit version by `CelEnvironmentBuilder.AddExtension`: `strings` 5, `math` 3, `lists` 4, `sets` 0, `encoders` 1, `bindings` 1, `two-var-comprehensions` 0, `network` 1, `optional` 2 with the optional syntax `e.?f`, `e[?k]`, `[?e]`, `{?k: v}` and `T{?f: v}`, and `protos` 0. An application builds sets of its own with `CelExtension.Create`. `Build` checks the sets and reports every conflict at once. See [Extension sets](docs/extensions.md).
- The type `decimal`, only on .NET 11: an IEEE 754 decimal128 number of 34 significant digits, with `CelType.Decimal`, `CelValue.FromDecimal`, the extension set `decimal` version 1 and, after `CelEnvironmentBuilder.EnableDecimalLiterals()`, the literals `12.34m` and `100m`. See [Decimal](docs/decimal.md).
- Data of the application as variables, bindings and results: numbers, `string`, `Guid`, enumerations, bytes, time (`DateTimeOffset`, `DateTime` of the kind `Utc`, `TimeSpan`, `CelTimestamp`, `CelDuration`), `Nullable<>`, arrays, lists, sets, dictionaries, `JsonElement`, `object`, `CelValue`, `CelList` and `CelMap`, converted without reflection. See [Type mapping](docs/type-mapping.md).
- Objects of the application. A source generator reads a type context — a `partial` class derived from `CelTypeContext` with `[CelObject]` attributes, with `[CelName]`, `[CelIgnore]` and the naming policies `CelNamingPolicy.CamelCase`, `AsIs` and `SnakeCaseLower` — and writes the descriptions of the listed types and of the types their members reach, so that a field is read by a direct access under JIT and under Native AOT; the diagnostics `GPCEL001` to `GPCEL009` say what it cannot describe. Types can also be described at run time with `CelObjectTypeBuilder` and supplied by a `CelTypeProvider`. See [Source generator diagnostics](docs/generator-diagnostics.md) and [Types described at run time](docs/runtime-types.md).
- Messages of protobuf, in the package `Great.Parts.Cel.Protobuf`: `CelProtobufTypesBuilder` takes the files that `protoc` generated for C# and the typed extensions of proto2, and the provider it builds gives an environment the messages, their fields, object literals, the equality of messages, `google.protobuf.Any` with its unpacking and the well-known types of `google/protobuf`. See [Protobuf messages](docs/protobuf.md).
- Functions of the application: `CelEnvironmentBuilder.AddFunction` with a .NET delegate or a `CelFunctionDecl` of overloads, `AddFunctionImplementation`, and a cost function (`CelOverloadDecl.WithCost`). See [Application functions](docs/recipes/application-functions.md).
- An environment described in JSON, read by `CelEnvironmentJson.Apply`: variables, functions, extension sets and object types of the application, with the place of every error in the JSON text. See [Environment description in JSON](docs/environment-json.md).
- Time zones for the receivers of `timestamp` and `duration`: `CelTimeZoneDatabase.Create` reads the TZif files of the application, and `CelEnvironmentBuilder.UseTimeZones` gives them to an environment. The library reads no files and no data of the operating system. See [Time zone database](docs/recipes/time-zone-database.md).
- Protection from untrusted expressions: limits of the length and of the nesting of an expression, a cost limit for an evaluation (`CelEvalOptions.CostLimit`) with a published unit for every operation, and cancellation with a `CancellationToken`. See [Limits](docs/limits.md) and [Cost](docs/cost.md).
- The result of the cel-spec conformance suite on every platform of the matrix, with the skip list and the result on the master branch of cel-spec. See [Conformance](docs/conformance.md).
- An attestation of origin for each `.nupkg` package on nuget.org, and the command that checks it. See the [README](README.md#where-the-packages-come-from).
